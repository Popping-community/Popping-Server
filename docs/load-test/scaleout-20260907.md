# 단일 DB Scale-out 재측정 — 2026-09-07

## 결론

현재 애플리케이션 코드와 동일한 단일 MySQL Primary를 사용해 App 1대 직접 연결(A)과 HAProxy + App 2대(B)를 비교했다. 구성별 유효 측정 3회의 중앙값 기준으로 TPS는 `464.89/s`에서 `516.08/s`로 `11.01%` 증가했고, 평균 응답시간은 `194.33ms`에서 `87.14ms`로 `55.16%` 감소했다. 모든 유효 측정의 오류율은 `0%`였다.

App 2대 구성에서는 각 App의 CPU 여유가 생겼지만 단일 1코어 MySQL이 100%에 도달했다. 따라서 이 결과는 App 계층의 병목이 DB로 이동했음을 보여주며, App 수 증가만의 순수 인과 효과나 시스템의 최대 처리량을 증명하지 않는다. B에는 HAProxy 추가와 App 총자원 증가가 함께 포함된다.

## 비교 조건

| 항목 | A — Before | B — After |
| --- | --- | --- |
| 진입점 | App 직접 연결 | HAProxy |
| App | 1대, `2 CPU / 2GiB` | 2대, 각각 `2 CPU / 2GiB` |
| JVM | App당 `Xmx 240MiB` | App당 `Xmx 240MiB` |
| HAProxy | 없음 | `0.5 CPU / 128MiB` |
| DB | MySQL Primary 1대, `1 CPU / 1GiB` | 동일 |
| Replica / Redis | 사용 안 함 | 사용 안 함 |
| HikariCP | App당 30 | App당 30, 총 60 |
| 부하 | JMeter 5.6.3, 500 VUser, ramp 60초, 600초 | 동일 |
| 세션 | Tomcat 메모리 세션 | `SERVERID` 쿠키로 App 고정 |

- 실행 순서는 순서 효과를 줄이기 위해 `ABBAAB`로 고정했다.
- 각 슬롯은 새 JVM으로 시작했다.
- 별도 600초 워밍업을 반복하고, 활성 JVM의 마지막 120초 JIT 증가율이 모두 2% 이하일 때 측정을 허용했다. 슬롯당 워밍업은 최대 3회였다.
- 측정값은 600초 본 측정 중 `[480,600)` 구간을 사용했다. Grafana 이미지는 대표 본 측정의 전체 600초를 보여주며 별도 워밍업을 포함하지 않는다.
- 정상상태는 `[180,300)` 대비 `[480,600)` 변화와 마지막 120초 내부 두 구간의 기울기를 함께 판정했다.

## 결과

| 지표 | A 중앙값 | B 중앙값 | 변화 |
| --- | ---: | ---: | ---: |
| TPS | 464.89/s | 516.08/s | +11.01% |
| 평균 응답시간 | 194.33ms | 87.14ms | -55.16% |
| p50 | 175ms | 68ms | -61.14% |
| p95 | 403ms | 238ms | -40.94% |
| p99 | 611ms | 362ms | -40.75% |
| Max | 1,856ms | 913ms | -50.81% |
| 오류율 | 0% | 0% | 동일 |

- A 유효 TPS 범위: `456.22–465.61/s`
- B 유효 TPS 범위: `513.93–534.28/s`
- A는 본 측정 6회 중 3회가 정상상태 또는 JIT 기준을 충족하지 못해 제외됐다.
- B는 본 측정 3회가 모두 기준을 충족했다.
- 제외 결과도 원본 실행 디렉터리에 보존했으며 유효 결과로 대체하거나 삭제하지 않았다.

대표 실행은 중앙 TPS에 가장 가까운 A의 `single-db-20260907-03-4A-measure2`와 B의 `single-db-20260907-03-2B-measure1`이다.

## 병목 이동

대표 측정의 마지막 120초 평균 CPU는 다음과 같다.

| 구성 | App CPU | MySQL CPU | HAProxy CPU |
| --- | ---: | ---: | ---: |
| A | 204.9% | 82.6% | 없음 |
| B | App-1 161.4%, App-2 137.7% | 102.4% | 39.1% |

A에서는 App 1대가 2코어 한계에 도달했다. B에서는 App CPU가 두 인스턴스로 분산됐지만 MySQL이 1코어 한계에 도달했다. 처리량 증가가 11%에 머문 반면 지연시간이 55% 감소한 이유는 App 대기열은 줄었지만 다음 병목인 DB가 처리량 상한을 형성했기 때문이다.

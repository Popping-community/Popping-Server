# 실증 스크립트

앱을 2대로 늘린 뒤 드러난 문제들을 **실패 주입으로 재현**하는 스크립트다.
`../measurement-protocol.md`가 A/B 측정 절차를 고정하듯, 여기 있는 것들은
"그 문제가 실제로 있다"를 보이는 실험을 고정한다.

| 스크립트 | 무엇을 보이나 |
| --- | --- |
| `capture_session.sh` | 인스턴스를 죽이면 거기 붙어 있던 사용자가 로그아웃된다 (Redis 이전 전) |
| `capture_session_after.sh` | 같은 실험을 Redis 이전 후에 돌린 결과 |
| `cache_capture.sh` | app-1에 쓴 댓글이 app-2에 안 보인다 (인프로세스 무효화) |
| `ws_test.py` | app-1에서 발생한 좋아요가 app-2 구독자에게 안 간다 (`enableSimpleBroker`) |
| `verify_redis_session.sh` | Redis 세션 도입 후 용량·분산·에러 1패스 검증 |

## 전제 조건

- 로컬 Docker Compose 스택이 떠 있을 것 (`popping-app-1`, `popping-app-2`, `popping-haproxy`, `popping-redis`)
- 컨테이너에 직접 붙으므로 도커 네트워크 이름이 필요하다
  ```
  docker inspect -f '{{range $k,$v := .NetworkSettings.Networks}}{{$k}}{{end}}' popping-app-1
  ```
- 테스트 계정(`user86`)과 게시글(`board-1/121`)이 있을 것
- `verify_redis_session.sh`는 JMeter가 `C:/apache-jmeter-5.6.3/bin`에 있다고 가정한다

## 이 스크립트들이 실제로 하는 일

명령을 나열하는 게 아니라, **실패한 실험이 통과한 실험처럼 보이는 상황**을 피한다.
이 프로젝트에서 세 번 속았고, 그 회피가 코드에 들어 있다.

**① 죽일 인스턴스를 하드코딩하지 않는다.**
HAProxy가 첫 요청을 라운드로빈으로 배정하므로 세션이 어디에 붙을지는 실행마다
다르다. 컨테이너 이름을 고정하면 절반 정도는 엉뚱한 쪽을 죽이고, 그러면
`200 OK`가 나온다. 그건 "문제 없음"이 아니라 **"실험 실패"인데 겉보기가 똑같다.**
그래서 `SERVERID` 쿠키를 읽어 대상을 정한다.

**② 캐시·WebSocket 실험은 HAProxy를 거치지 않는다.**
프록시를 통하면 어느 인스턴스가 응답했는지 통제되지 않는다. 처음에 `SERVERID`
쿠키를 손으로 만들어 붙였다가 HAProxy가 그걸 받아들이지 않아 두 요청이 모두
라운드로빈으로 흘렀고, **양쪽 다 정상으로 보였다.** 도커 네트워크에서 컨테이너에
직접 붙는 방식으로 바꾼 이유다.

**③ 대조군 없이 "0건 수신"을 결론으로 쓰지 않는다.**
`ws_test.py`는 교차 인스턴스 수신이 0건인 것만 보지 않는다. 같은 구독자에게
자기 인스턴스에서 발생한 이벤트를 보내 1건 수신을 확인한다. 이게 없으면
"브로커가 인스턴스를 안 넘는다"와 "내 클라이언트가 고장났다"를 구분할 수 없다.

**④ Redis에서 세션을 확인할 때 `--scan`을 쓰지 않는다.**
부하테스트가 남긴 세션이 수백 개 있어서, 스캔 결과는 **내 세션이 아닌 키**일 수
있다. "세션이 하나 있다"는 "내 세션이 여기 있다"와 다른 주장이다. 쿠키를 base64
디코드해 그 키를 `EXISTS`로 직접 조회한다.

## 캡처가 실제 실행과 일치하는 이유

블로그 캡처를 만드는 세 스크립트(`capture_session.sh`, `capture_session_after.sh`,
`cache_capture.sh`)는 명령 문자열 하나를 출력하고 그대로 `eval` 한다.

```bash
run() { printf '$ %s\n' "$1"; eval "$1"; printf '\n'; }
```

출력된 명령과 실행된 명령이 같은 문자열에서 나오므로 어긋날 수 없다.
읽는 사람이 한 줄씩 복사해 붙여도 같은 결과가 나온다.

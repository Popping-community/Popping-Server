# 댓글 캐시 OFF의 작성자 최신성과 비용 — 2026-09-22

## 확인한 최신성 범위

현재 소스와 이전에 검증한 동일 JAR를 사용해 실제 MySQL Primary/Replica와 앱 두 대를 별도 Compose 프로젝트에서 실행했다. 애플리케이션 코드는 이번 실험에서 바꾸지 않았다. 원래 Popping 컨테이너와 DB는 수정하지 않았다. 게스트 작성·삭제와 첫 페이지 조회만 검증했으며, 로그인 세션·실제 HAProxy·원격 배포 검증은 포함하지 않았다.

| 시나리오 | 확인 결과 |
|---|---|
| 복제 적용 정지, 앱1→앱2 및 앱2→앱1 작성 후 즉시 조회 | 총 10회, 성공 쿠키 전달 및 댓글 ID/개수 일치 |
| 같은 상태에서 쿠키 없는 클라이언트 조회 | 이전 Replica 상태를 읽음. 음성 대조 성립 |
| 복제 적용 정지, 양방향 삭제 후 즉시 조회 | 2회, 작성자는 삭제 반영, 쿠키 없는 조회에는 이전 댓글 존재 |
| 쿠키를 자연 만료시킨 후 조회 | 2회, 쿠키 미전송 및 이전 Replica 상태로 되돌아감 |
| 복제 적용 재개 및 소스 위치 도달 확인 후 조회 | 2회, 변경된 상태 확인 |
| 댓글 INSERT 후 부모 UPDATE에서 DB 오류 주입 | 2회, HTTP 500 및 INSERT 롤백, 성공 쿠키 미발급 |
| 입력 검증 실패 | 2회, HTTP 400 및 성공 쿠키 미발급 |

위 20개 관측 케이스가 통과했다. 여기에 포함된 GET 28건의 HTTP 시작/종료 시간·게시글 ID와 MySQL general log의 댓글 트리 CTE를 독립 대조했다. 각 요청 구간에 기대한 DB에서 CTE 1회, 반대 DB에서는 0회를 확인했다. 성공 응답이나 데이터 일치만으로 Primary 라우팅을 추측하지 않았다. 실패 주입 2건은 실제 SQL 로그에서도 INSERT → UPDATE → ROLLBACK 순서를 확인했다. 부모 카운터의 롤백 전후 별도 스냅샷은 남기지 않았으므로 그 부분의 독립 검증으로 확대하지 않는다.

추가 음성 대조에서는 앱2의 빈 댓글 캐시를 미리 채운 후, 앱1의 작성 성공 쿠키를 가지고 앱2를 조회했다. **쿠키가 실제 전송됐는데도 ON 앱2는 이전 빈 목록을 반환했고, 같은 쿠키로 조회한 OFF 앱1은 새 댓글을 반환했다.** 기존 쿠키만으로 캐시된 트리까지 최신화되지 않는다는 점을 실제 HTTP로 확인했다(`cache-on-sticky-control.json`).

**이것은 지속적인 read-your-writes 보장이 아니다.** 현재 코드는 성공 후 `Max-Age=3` 쿠키를 보낸다. 정상 발급·전달되고 유효한 동안의 요청이 Primary로 향하는 것을 검증했다. 쿠키 만료 뒤 Replica가 아직 뒤처져 있으면 본인이 방금 본 댓글도 사라져 보일 수 있다. 3초보다 긴 지연을 해결한 결과로 표현하지 않는다.

## 실험 구성과 실패 기록

- Compose 프로젝트: `popping-sticky-check-20260922`. 앱 포트는 loopback `19191`, `19192`. DB는 호스트 포트를 열지 않고 tmpfs만 사용했다.
- MySQL 8.4.9, server_id 721/722. Primary/Replica 각각 CPU 1 / 512MiB, 앱 각각 CPU 1 / 512MiB, JVM Xmx 256MiB, 풀 각각 5.
- 게스트 클라이언트는 CookieJar로 실제 Set-Cookie/만료를 처리한다. 앱 선택만 직접 바꾸어 교차 인스턴스 경로를 결정적으로 만든다.
- `STOP REPLICA SQL_THREAD`로 적용을 멈춘 뒤 Primary와 Replica의 실제 ID 차이를 확인했다. 재개 후 `SOURCE_POS_WAIT`로 읽기 전에 복제 위치 도달을 확인했다.
- 초기 `correctness-01.json`은 app2 기동 완료 전 검사를 시작했고 첫 POST에서 deadlock HTTP 500이 발생했다. 해당 실패는 보존했다. 정확한 deadlock 원인을 확정하지 않았으며 캐시 오류라고 해석하지 않는다. 양쪽 readiness와 복제 동기화를 선행하도록 하네스를 수정한 후 `correctness-02.json`이 통과했다. 초기 실행은 성공 표본에 포함하지 않았다.
- 생성 응답마다 동일한 `STICKY_PRIMARY` Set-Cookie가 2개, 삭제에는 1개 관측됐다. 테스트 클라이언트에서는 같은 값으로 처리되어 기능 문제가 없었지만 중복 콜백 등록은 후속 정리 대상이다. 이번에 별도 기능 변경은 하지 않았다.

## 비용 비교

사전 계획은 `_workspace/cache-consistency/2026-09-22/run-02-sticky/cost-plan.md`에 기록했다. 합성 데이터는 큰 게시글 1개 × 댓글 10,000개와 작은 게시글 100개 × 각 100개 댓글이다. 총 댓글 20,000개이며 10개 단위의 root 1 + child 9 구조다. 원래 운영/대규모 실험 데이터의 분포를 재현했다고 주장하지 않는다.

각 분포에서 초당 50건을 30초간 예약해 1,500건씩 보냈다. 워밍업은 구간마다 고정 20초, 순서는 ON/OFF/OFF/ON/ON/OFF이고 중간에 ON/OFF를 맡는 앱을 교환했다. 분포·조건별 3회, 총 12개 측정 구간 18,000건이다. 모든 응답에서 첫 100개 댓글 ID와 totalComments를 검증했고 오류/내용 불일치는 0건이었다. 실제 최대 동시 클라이언트는 32개이므로 포화 시 생성기 큐에도 대기가 쌓인다.

다음은 **개별 실행 지표의 중앙값**이다. 여러 실행의 요청을 합쳐 구한 p95가 아니다.

| 합성 분포 / 설정 | 요청 실행 후 p95 | 예약 시점부터 응답까지 p95 | 1,500건 처리 완료 시간 | Replica CPU | 측정 구간 CTE 수(3회) |
|---|---:|---:|---:|---:|---|
| 10,000댓글 글 집중 / ON | 142ms | 274ms | 30.01초 | 5.69% | 0 / 0 / 0 |
| 10,000댓글 글 집중 / OFF | 1,612ms | 39,274ms | 71.24초 | 99.70% | 1,500 / 1,500 / 1,499 |
| 100댓글 글 100개 분산 / ON | 73ms | 196ms | 30.00초 | 5.63% | 0 / 0 / 0 |
| 100댓글 글 100개 분산 / OFF | 121ms | 359ms | 29.99초 | 8.41% | 1,500 / 1,500 / 1,500 |

집중 OFF의 처리 완료 시간은 3회 모두 70.29~72.40초, CPU는 99.58~99.74%였다. 따라서 이 합성 집중 조건에서는 예약한 50req/s를 계속 처리하지 못했다. 요청 실행 시간만 보면 생성기 대기 약 37~39초를 놓치므로 예약 시점 기준 지표를 함께 적었다. HTTP 오류 0%가 목표 처리량 충족을 뜻하지 않는다.

마지막 집중 OFF 구간의 performance_schema CTE count 증분은 1,499인 반면 응답은 1,500건이고 rows examined 증분은 15,150,000으로 다른 OFF 구간과 같았다. **이 1건의 계수 차이 원인은 확인하지 못했다.** 값을 1,500으로 보정하지 않았으며 CTE 수는 계측 증분으로 표현한다. 이 오차를 무시하고 요청별 정확한 1:1 계측이라고 주장하지 않는다.

앱을 재생성해 캐시를 비운 별도 20개 동시 요청에서는 ON의 CTE가 **1회**, OFF는 **20회**였다. 모두 응답 ID/개수 검사를 통과했다. per-key 로딩 병합을 OFF에서 잃는 비용이 실제 DB 실행에도 나타났다.

한계:

- CTE 시간·rows examined는 해당 digest만의 값이다. ON에서도 좋아요 메타데이터 조회가 남으므로 전체 DB 쿼리가 0건이라는 뜻이 아니다. CPU는 Replica 전체 cgroup의 값이며 CTE 전용 CPU가 아니다.
- 고정 워밍업은 JIT/정상상태 검증이 아니다. ON의 요청 실행 p95도 집중 76~162ms, 분산 30~125ms로 흔들렸다. 전용 생성기나 운영 SLO가 없는 로컬 합성 비교다.
- 기존 컨테이너는 켠 상태로 보존했다. CPU/메모리 한도, 동일 호스트 생성기, 공유 DB 버퍼와 실행 이력의 영향을 배제하지 못한다. 이 표를 운영 개선율·최대 TPS·통계적 유의성으로 일반화하지 않는다.
- 본 비용 비교는 쓰기 없는 게스트 조회다. ON은 성능 대조군이며 교차 앱 최신성에 적합한 구현으로 승인한 것이 아니다.

## 결정

**댓글 캐시 OFF를 최종 운영 정책으로 확정하지 않는다.** 로컬 캐시 문제와 작성자 최신성은 재현·검증했지만, 큰 글에 조회가 몰릴 때 OFF의 비용도 확인했다. 다음 최소 후보는 **작성 직후의 요청만 캐시를 우회해 기존 Primary 라우팅을 사용하고, 일반 조회는 Caffeine의 per-key 로딩을 유지하는 방식**이다. 전체 Primary 강제와 새 Pub/Sub 인프라를 먼저 도입하지 않는다.

이 실험 종료 당시에는 기본 OFF 패치를 유지했고 새 후보는 구현 전이었다. 이후 [작성자 우회 + 일반 조회 ON·TTL 5초](comment-cache-hybrid-20260922.md)를 구현·검증했다. 이 문서의 ON/OFF 수치는 당시 대조군의 결과다. 캐시 만료와 Replica 최신화는 별개이므로 TTL만으로 최신성 상한을 보장하지 않는다. 당시 후속 동작·수용 조건은 `_workspace/cache-consistency/2026-09-22/run-02-sticky/next-design.md`에 보존했다. 원격 배포는 하지 않았다.

측정 종료 후 프로젝트 label을 확인한 임시 컨테이너 4개와 전용 네트워크만 제거했다. 원래 Popping 컨테이너 10개는 계속 실행 중인 것을 확인했다. 임시 DB는 tmpfs였으며 HTTP·SQL 로그와 결과 JSON은 보존했다.

# 변경별 JMeter 검증 — 첫 기준 버전 워밍업 중단

2026-09-29. 사전 계획: [검증 프로토콜](change-load-20260929-plan.md).

## 결론

첫 기준 버전 A의 20분 워밍업이 사전 JIT 조건을 통과하지 못해 캠페인을
중단했다. 변경별 성능 비교는 아직 성립하지 않았고 B~E는 실행하지 않았다.
오류 없는 워밍업을 본 측정 성공이나 운영 용량으로 해석하지 않는다.

| 검사 | 관측 | 판정 |
| --- | --- | --- |
| 30초 smoke | 부모 354건, redirect child 34건; 실패 0건 | 통과 |
| 20분 warmup | 부모 523,547건; 실패 0건 | 요청 정상 |
| 저장된 redirect child | 4,312건; 실패 0건 | 정상 |
| CSV | 손상 행 0건; 관측 1,199.661초 | 길이 조건 통과 |
| 18분 JIT 증가율 | 최근 약120초 / 누적 컴파일 시간 = 2.3003% | 기준 <=2% 미달 |
| 20분 JIT 증가율 | 같은 계산 1.0509% | 통과 |
| 종합 | 두 시점 모두 통과해야 함 | 본 측정 미실행 |

JIT 증가율은 CPU 사용률이나 요청 지연 비율이 아니다. 워밍업 마지막120초의
부모 TPS486.9, p99=445ms는 **제외된 워밍업의 진단 수치**이며 성능 비교 표에
포함하지 않는다. 전체 워밍업의 초기 참조 구간 대비 처리량은 약32% 높아져
분석기는 WARMING으로 분류했다. 이를 별도900초 측정의 안정성 판정으로
대체하지 않았다.

## 자원 관측과 해석

15초 간격 원본 관측81개에서 호스트 최소 여유 RAM은 약2.215GiB였다.
앱·DB의 cgroup OOM/OOM-kill 이벤트는 모두0이었다. 관측 구간 평균 CPU는
앱 약1.981코어(한도2), DB 약0.676코어(한도1)였다. 표본 수집은 최대2.379초였다.
따라서 이번 중단을 RAM 부족으로 단정할 근거는 없고, 직접 중단 원인은
사전에 정한 JIT 안정화 검사 미통과다. CPU 포화와 컴파일의 인과를 이 한 번의
관측으로 분리해 입증하지는 않았다.

## 실제 Grafana 캡처

로컬 전용 Grafana에서 정확한 워밍업 시간 범위로 PNG를 렌더링했다.
렌더링은 실험 앱·DB·프록시를 제거한 뒤 수행했다.

- 응답 시간, 서버 요청량, JIT: 데이터와 이미지 확인.
- CPU, DB 읽기: No data. Windows CRLF가 Prometheus 숫자 파싱을 깨뜨린
  수집기 결함을 확인했다. 해당 빈 PNG는 보존하되 증거로 사용하지 않는다.
- 독립 원본 `resources.jsonl`의 CPU/DB 기록은 남아 있다. 이를 Grafana의
  실시간 수집 자료인 것처럼 역으로 채우거나 이미지를 재구성하지 않았다.
- 후속 실행용 exporter 줄바꿈을 LF로 고쳤고, 빈 시계열 패널은 캡처 성공으로
  집계하지 않도록 검사했다. 앱 비즈니스 코드는 변경하지 않았다.

캡처·시계열·해시·시각 검사 위치:
`_workspace/change-load/2026-09-29/campaign-f856516f7666/runs/01-A-warmup/grafana/`.
원본 JMX/CSV, 5개 소스·JAR 해시, 이미지 ID, DB seed 검증, run.json, JTL 및
자원 기록은 같은 캠페인 디렉터리에 보존했다.

댓글 캐시 글에는 B→C, 조회수 동시 집계 글에는 C→D의 유효한 비교가 필요하다.
이번 A 워밍업 캡처를 그 변경의 성능 효과처럼 두 글에 추가하지 않았다.
게시글 상세 캐시 OFF 결과의 글 위치도 아직 사용자 선택 대기다.

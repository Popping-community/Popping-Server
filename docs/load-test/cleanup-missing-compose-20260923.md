# Compose 유실 시 정리 실패를 구분하기 (2026-09-23)

## 수정한 문제

`CleanupGuard.cleanup()`은 생성 시도가 없거나 Compose 파일이 없으면 같은 `no_owned_creation_attempt` 결과를 반환했다. 생성한 자원이 남아 있는데 파일만 사라진 경우도 정상 생략처럼 기록할 수 있었다.

두 조건을 분리했다. 생성 시도 전이면 기존처럼 생략한다. 생성 시도 후 파일이 없으면 정리 콜백을 호출하기 전에 RuntimeError를 던진다. 기존 `run_preserving_failure`가 이를 `cleanup_error`에 기록한다. 원래 작업도 실패했다면 동일한 원래 예외 객체와 `error`를 유지하며, 원래 작업이 성공했더라도 정리 실패가 실행 실패로 드러난다.

이는 자원 유출의 자동 복구가 아니라 **정리를 못 했다는 사실을 숨기지 않도록 한 수정**이다.

## 선택지

| 방법 | 판단 |
|---|---|
| 기존의 정상 생략 결과 유지 | 생성 이력을 부정하고 후속 확인을 빠뜨릴 수 있어 제외 |
| 파일 없이 추정한 Compose 명령 또는 ID 직접 삭제 | 기존 정리 정의·소유권 검증 경로를 우회하므로 제외 |
| 명시적 오류, 이력 보존, 원본 복원 후 검증된 재시도 | 기존 예외 보존 도우미를 활용할 수 있어 채택 |

별도 예외 계층이나 자동 복구 엔진을 추가하지 않았다. `owned_ids`와 `creation_attempted`를 그대로 유지하며, 원본 파일을 복원한 후 기존 ID 검증을 거쳐 정리할 수 있다.

## 테스트 근거

보존 위치: `_workspace/deploy-safety/2026-09-23/cleanup-missing-v1/`.

| 실행 | 결과 | 범위 |
|---|---|---|
| baseline | 14개 중 실패3·오류1 | 기존10개+신규4개. `cleanup_error`가 없어 KeyError가 난 경우 포함 |
| fixed | 50개 통과, 실패·오류·건너뜀0 | scripts/deployment의 전체 unittest |
| docker-proof | 실패 주입2경우 통과 | 네트워크 없는 실제 컨테이너1개, 파일 유실·원래 작업 성공/실패 |

신규4개 단위 테스트는 생성 뒤 파일 유실, 부분 생성 실패와 파일 유실이 겹친 경우, 본 작업 성공 후 정리 실패, 원본 복원 후 정리 재시도를 확인한다. 파일 유실 상태에서 list/verify/remove 세 콜백 모두 미호출, 소유권 이력 보존, 원래 예외 객체 유지도 검사한다.

실제 Docker 실험에서는 로컬 Redis 이미지의 정확한 image ID를 사용하되 실행 명령은 `sleep 300`, `network_mode: none`으로 두었다. 사용자 요청을 처리하는 서비스는 아니다. 고유 project/label 아래 생성한 컨테이너1개에 대해 다음을 확인했다.

1. Compose 파일을 같은 실험 폴더 안의 별도 이름으로 옮겨 원래 경로에서 읽을 수 없게 했다.
2. 본 작업 성공과 본 작업 실패를 각각 주입했다. 두 경우 모두 `cleanup_error`가 기록됐으며, 후자는 원래 예외 객체도 유지됐다.
3. 파일 유실 동안 정리 콜백 호출은 모두0회였다. 별도 read-only inspect로 정확히 같은 컨테이너가 실행 중임을 확인했다.
4. SHA-256이 같은 원본 파일을 원래 경로로 복원한 뒤, ID·image·label 검증을 거쳐 `compose down --volumes`를 수행했다. 소유한 컨테이너1개가 정리됐고 해당 project의 잔여 컨테이너는0개였다.
5. 시작 시 실행 중이던 기존10개 컨테이너 ID가 종료 후에도 실행 중임을 확인했다. 모든 설정의 불변을 검증했다는 의미는 아니다.

실제 Docker에서 부분 생성 자체를 실패시킨 것은 아니다. 그 경로는 단위 테스트 근거와 구분한다. 실패한 파일 유실 시도와 복원 후 정리는 `docker-proof/result.json`의 서로 다른 필드로 남겼다.

## 검수와 한계

독립 Codex 검수가 helper·신규 테스트·Docker 실험 스크립트를 읽었고 blocker를 발견하지 않았다. Claude 재검수는 사용 한도로 아직 미완료다.

단일 호출자와 고유 namespace 전제는 유지된다. 파일 확인과 실제 정리는 원자적이지 않으며, 원본과 다른 Compose 파일 교체나 다중 controller 간 경합까지 해결하지 않았다. helper 자체는 복원 파일의 내용을 해시로 검증하지 않는다. 이번 rig가 원본 해시를 확인한 것은 실험의 복원 절차다.

이번에는 Python 도구만 수정했으므로 Java216개를 다시 실행하지 않았다. 해당 결과를 새 검증으로 재사용하지 않는다. 운영 앱 배포·기존 컨테이너 변경도 수행하지 않았다. 기존 역사 실험 디렉터리는 수정하지 않았다.

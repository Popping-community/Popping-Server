# Post 상세 캐시의 서버 간 불일치 — 재현·최소 수정 (2026-09-24)

## 결과와 범위

같은 Primary MySQL을 쓰는 두 실제 JVM에서 App2의 게시글 제목·본문 수정, 댓글 추가, 게시글 삭제가 커밋된 뒤에도 App1은 로컬 Caffeine의 이전 상세 응답을 반환했다. 기본 설정에서 Post 상세 캐시를 등록하지 않도록 바꿨다. 기존 서비스의 캐시 부재 시 DB 조회 경로와 무효화의 null 처리를 재사용한다.

설정은 `app.cache.post-detail.enabled=false`가 기본이다. 명시적 `true`는 이전 30분 로컬 캐시를 켜며 서버 간 stale 응답도 다시 발생한다. 댓글 캐시와 게시판 캐시 정책, DB 라우팅은 유지했다. 로컬 캐시 잔존을 제거한 변경이며 Replica 지연까지 해결한 것은 아니다. 실행 중인 기존 서비스에 배포하지 않았다.

## 실제 HTTP 검증

각 사례마다 별도 게시글을 만들고 두 앱에서 상세를 먼저 읽었다. 게스트 게시글 생성·비밀번호 확인·수정·삭제 및 댓글 추가는 실제 HTTP 컨트롤러/서비스/트랜잭션을 통과했다. 이후 앱별 HTML과 DB 행, Prometheus의 `postDetail` hit/miss를 따로 저장했다. 복제 DB는 없으며 애플리케이션 설정은 단일 `spring.datasource.url`만 사용한다.

| 사례 | 기존/opt-in App1 | 쓰기를 처리한 App2 | 기본 off의 두 앱 |
|---|---|---|---|
| 제목·본문 수정 | 이전 제목·본문 | 새 제목·본문 | 새 제목·본문 |
| 댓글 추가 | 댓글수 0 | 댓글수 1 | 댓글수 1 |
| 게시글 삭제 | 삭제 전 상세 유지 | POST_NOT_FOUND 화면 | POST_NOT_FOUND 화면 |

삭제 결과는 단순히 제목이 없는지에 그치지 않고 보존 HTML에 `POST_NOT_FOUND`가 있으며 `INTERNAL_ERROR`는 없는지 확인했다. 현재 MVC 예외 처리의 HTTP 상태는 200이다. 이 변경을 HTTP404 수정으로 표현하지 않는다. 원래 무인증 API/회원 권한/공유 세션 전체를 새로 검증한 것도 아니다.

기본 off와 opt-in 대조군은 **같은 JAR SHA-256** `b8459f9f7c7340687c50ce4b2bc309b837294a927c49e2fcabd18de092db4def`를 사용했다. 각 앱 컨테이너 안의 JAR 해시도 확인했고 주입된 소스 스냅샷과 현 소스를 재대조했다. 이 JAR는 작업 트리에서 빌드한 로컬 산출물이며 커밋된 릴리스가 아니다. 내장 application 설정 파일은 제거하고 비밀정보 없는 격리 설정만 사용했다.

## 30분 TTL과 30초 flush를 구분해야 하는 이유

현재 상세 GET은 해당 JVM의 조회수 pending에 증가분을 남긴다. 정상적인 조회수 scheduled flush가 실행되면 **그 JVM의** 상세 캐시도 지운다. 따라서 실제 stale 응답을 무조건 30분 동안 유지한다고 말할 수 없다. 첫 실험에서는 제목·본문 stale은 보였지만 댓글수 검증 사이에 flush가 캐시를 지워 양쪽이 1을 반환했다. 이 시도를 실패 이력으로 보존했다.

성공한 기존 코드 재현은 자연스러운 App1 flush 뒤 다시 캐시를 채운 후 쓰기와 읽기를 수행했다. 후속 opt-in 대조군은 pending과 in-flight를 함께 확인하도록 보강했다. 두 지표는 최종 캐시 evict보다 먼저 0이 될 수 있으므로 무효화 완료 장벽이 아니다. 과거 파일의 refill-after-flush라는 이름도 완료 증명으로 해석하지 않는다. 최종 응답·DB·hit/miss를 재현의 근거로 삼았으며 반복 재현이 경합 없이 안정적이라고 주장하지 않는다. 정상 flush가 stale을 우연히 없애는 동작은 무효화 전파나 최신성 보장이 아니다.

## 대안 비교와 선택

| 방법 | 얻는 것 | 남는 문제/추가 비용 | 이번 판단 |
|---|---|---|---|
| 상세 캐시 off | 로컬 상세 DTO가 변경·삭제 후 남지 않음 | 상세 DB 조회 추가, Replica 지연은 별도 | 기본값으로 적용 |
| 짧은 TTL | 로컬 캐시 보관 시간을 줄임 | 만료 전 stale·삭제 글 노출 유지, 허용 시간 근거 필요 | 미채택 |
| 쓰기 후 sticky 우회 | 해당 작성자의 Primary 읽기에 유리 | 다른 사용자·쿠키 만료 후 읽기는 해결 못함 | 단독 해결책으로 미채택 |
| 공유 캐시/무효화 전파 | 앱 간 캐시 상태 조율 가능 | DB 커밋과의 순서, 이벤트 유실, 장애 복구, 진행 중 로더의 재적재 처리 추가 | 현재 범위에 비해 커서 보류 |

Caffeine의 expireAfterWrite는 엔트리 생성/교체 기준의 만료 정책이다. [Caffeine 공식 문서](https://github.com/ben-manes/caffeine/wiki/Eviction). Redis Pub/Sub은 at-most-once 전달이므로 이를 도입하는 것만으로 무효화 유실 문제가 사라지지 않는다. [Redis 공식 문서](https://redis.io/docs/latest/develop/pubsub/). 위 선택은 이 코드와 실험에 대한 판단이며 두 대안을 구현·성능 측정했다는 뜻이 아니다.

## DB 조회 비용

신선한 격리 환경의 각 앱에서 상세를 한 번 읽은 후 비로그인 순차 GET 20회를 수행했다. DB performance_schema statement digest의 전후 차이를 비교했다.

| 20회 요청 동안의 SELECT | 기본 off | 명시적 opt-in |
|---|---:|---:|
| Post 상세를 가져오는 ORM SELECT | 20 | 0 |
| guest identity 개인 반응 SELECT | 20 | 20 |

캐시를 끄면 이번 경로에서는 요청당 Post 조회가 하나 더 필요했다. 요청 지연 원자료도 보존했지만, 단일 게시글·순차 20회·각 1회 실행이며 JVM 가동 시간과 앞선 시나리오 대기 시간도 다르다. 용량, p95 개선율, 최대 트래픽에서의 DB 여유를 증명하지 않는다. 기본값은 로컬 잔존 제거를 우선한 선택이며 운영 채택 전 대표 트래픽에서 DB 비용을 확인할 필요가 있다.

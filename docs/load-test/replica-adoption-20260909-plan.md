# 단일 DB에서 Read Replica 도입으로 전환하는 재검증 계획

상태: **2026-09-09 13:47 KST 실행 시작**(`replica-20260909-adoption-01`). 아래는 실행 전에 정한 비교 대상과 판정 기준이며 이 문서 자체는 실행 결과가 아니다. 원래 실험 자료, 블로그의 과거 기록, 현재 사용자 소스는 보존한다.

## 이번에 답할 질문

500 VUser에서 App 2대가 사용하는 **Primary 1대 구성에 Read Replica를 추가하면**, HTTP 처리량·응답시간·DB 부담·복제 최신성이 어떻게 달라지는지 확인한다. A는 실제로 Replica 컨테이너를 중지하고 Primary만 실행한다. B는 Primary와 Replica를 각각 1 CPU / 1 GiB로 실행한다.

이는 DB 총 CPU가 1에서 2로, DB 메모리 한도가 1 GiB에서 2 GiB로 증가하는 **도입 구성 전체의 효과**다. 같은 총자원에서 순수 읽기 라우팅 효과만 분리하는 비교가 아니다. 새로운 측정 절차·현재 코드·공통 연결 풀로 도입 전후를 재검증하므로 예전 글의 실행 조건을 그대로 재현했다고 표현하지 않는다.

이전 [9월 8일 안정화 진단](replica-stabilized-20260908.md)은 A/B 모두 DB 2대와 복제를 유지했으므로 별도 질문의 결과다. [0.5/1.5 CPU 재배분 진단](replica-500-reallocation-20260909.md)은 이번 B의 자원 배분을 바꾸는 후속 질문이다. 이번 실험에는 0.5/1.5 조건이나 300 VUser 조건을 섞지 않는다.

## 구성과 통제 조건

| 항목 | A: 단일 Primary | B: Read Replica 도입 |
|---|---|---|
| App / HAProxy | App 2대, 각 2 CPU / 2 GiB, 동일 HAProxy | 동일 |
| Primary | 1 CPU / 1 GiB, 읽기·쓰기 모두 처리 | 1 CPU / 1 GiB, 쓰기 및 Primary로 라우팅된 읽기 처리 |
| Replica | 기존 컨테이너 완전 중지 | 기존 컨테이너 실행, 1 CPU / 1 GiB |
| DB 총 CPU / 메모리 한도 | 1 CPU / 1 GiB | 2 CPU / 2 GiB |
| 앱 read pool | Primary에 연결 | Replica에 연결 |
| 앱 write pool | Primary에 연결 | Primary에 연결 |
| 앱별 Hikari | write max 20 / read max 30, minimum-idle 각각 5 | 동일 |
| Sticky Primary | ON, 기존 3초 설정 | 동일 |
| 세션 | Redis 세션 OFF, JSESSIONID·SERVERID 앱 sticky | 동일 |
| 부하 | 500 VUser, 그룹별 300/150/5/5/40, ramp 60초 | 동일 |
| JMX·fixture·타이머 | 기존 검증된 입력을 해시로 고정 | 동일 |
| 워밍업 / 본 측정 | 슬롯마다 워밍업 600초 1회 / 본 측정 900초 1회, 재시도 없음 | 동일 |
| 데이터 | 쓰기 누적, 초기화·삭제 없음 | 동일 |

- 고정 이미지: `sha256:ea9b900246917cc43df83c6c55ca4ff3064ae13b942b447adbb8f86761e0c9e3`. 실행 전 소스 fingerprint와 일치 여부를 확인한다. 실험 중 다시 빌드하지 않는다.
- 실제 JVM 설정도 확인한다. 기존 기준은 최대 힙 240 MiB이며, 컨테이너 메모리 2 GiB를 JVM 힙 2 GiB라고 쓰지 않는다. 두 앱의 힙·JIT·GC 설정은 공통이다.
- Primary의 binlog·GTID·내구성 설정을 A에서도 그대로 유지한다. A에서 바꾸는 것은 Replica 실행 여부와 읽기 연결 대상이다. Replica B는 worker 2, `replica_preserve_commit_order=ON`, `log_bin`·`log_replica_updates=ON`을 유지한다. `sync_binlog=1`, `innodb_flush_log_at_trx_commit=1`을 낮추지 않는다.
- Sticky Primary는 이미 적용된 앱의 동작과 공통 코드 경로를 유지하려고 양쪽에서 켠다. A는 어느 풀을 선택해도 Primary에 연결된다. B에서는 쓰기 후 일부 읽기가 Primary로 갈 수 있다. 따라서 B를 모든 읽기가 Replica로 가는 조건이라고 표현하지 않는다. Sticky ON/OFF 효과나 3초 이내 read-your-writes 보장을 검증하는 실험이 아니다.
- A의 두 연결 풀이 동일한 Primary를 사용하더라도 풀을 하나로 합치거나 예전 max 50/80으로 되돌리지 않는다. 연결 풀 변경 효과를 함께 섞지 않기 위해서다.
- 두 DB의 저장소는 기존과 같은 공유 가상 장치에 둔다. Replica 추가로 발생하는 호스트 CPU·메모리·공유 저장소 부담은 이 로컬 도입 구성에 포함된다. 디스크의 독립 효과나 별도 호스트 배치의 효과를 주장하지 않는다.
- 이번 비교에 별도 상세 stage/file 이벤트 계측을 새로 켜지 않는다. 양쪽 공통 지표와 B 복제 지연·health를 수집하고, 계측 설정 변경이 필요하면 실행 전에 양쪽 공통 정책으로 명시한다.

## 반복수와 실행 순서

목표는 **A/B 각각 유효한 본 측정 3회**, 사전 순서는 **A → B → B → A → A → B**다. 각 슬롯마다 새 앱 프로세스를 준비하고 동일한 워밍업·안정화 절차를 거친다. 기존 완료 캠페인과 결과를 다시 실행하거나 덮어쓰지 않고 새 캠페인 ID와 독립 하네스를 사용한다.

3회는 작은 반복 실험의 변동 폭과 재현 여부를 보는 기준이다. 통계적 유의성이나 장기 용량을 입증하지 않는다. ABBAAB는 한쪽만 먼저 몰아서 실행하는 편향을 줄이지만, A의 평균 실행 위치는 3.33, B는 3.67로 완전한 시간 균형은 아니다. 쓰기 누적·DB 캐시·시간에 따른 호스트 상태는 여전히 해석의 한계로 남긴다.

각 슬롯은 **600초 워밍업 1회와 900초 본 측정 1회로 고정하며 자동 재시도는 없다.** 예정된 본 측정은 총 6회이고, 6개 슬롯의 부하 실행 시간은 150분이다. Smoke·GTID 회복·유휴 안정화·검증 시간은 별도다. 유효 회차 확보를 위해 추가 슬롯이나 추가 워밍업을 실행하지 않는다.

워밍업은 요청 오류·관측 coverage·입력 불변·JIT 기준을 모두 통과해야 하며 하나라도 실패하면 중단·복구한다. 본 측정의 요청 오류·관측 coverage 실패·입력 변경, 환경 격리 실패, 복제 health 오류, 안전 기준 위반도 중단·복구 사유다. **본 측정에서 TPS 정상상태 또는 JIT 기준만 통과하지 못한 경우에는 원시 결과와 제외 이유를 보존하고 예정된 다음 슬롯으로 진행한다.** 각 슬롯의 실제 실행 결과를 모두 공개하며, 6회 종료 후 A/B 각각 유효 3회를 확보하지 못했다면 확정 비교 기준 미달로 보고한다. 실패 결과를 새 시도로 대체하지 않는다.

**B의 lag UNSTABLE은 HTTP 측정의 제외 사유나 재시도 사유가 아니다.** HTTP 측정이 유효하면 해당 결과를 그대로 채택하고 복제 안정성 실패를 함께 기록한다. 좋은 lag가 나올 때까지 반복하지 않는다.

## 슬롯별 생명주기와 복제 전환

1. 실제 캠페인 시작 직전에 다른 캠페인·JMeter·태스크 컨테이너가 실행 중이지 않은지 확인한다. 그 시점의 기존 컨테이너 ID·실행 상태·자원·restart policy와 호스트 상태를 새 snapshot·journal로 기록한 후 실험 전 격리를 적용한다. 이전 readiness 시점의 상태를 복구 기준으로 재사용하지 않는다. 시작 시 Primary와 Replica의 복제 health·GTID 동기화를 확인한다.
2. 각 슬롯 전에는 기존 Replica를 실행한 상태로 앞선 쓰기를 모두 따라잡게 하고 유휴 상태를 확인한다. 이 전환 구간은 A/B 본 측정에 포함하지 않는다.
3. **A 슬롯은 앱 기동·smoke 전에 Replica 컨테이너를 완전히 중지**한다. `STOP REPLICA`만 실행하고 mysqld를 켜 둔 상태로 대체하지 않는다. Smoke·워밍업·유휴 안정화·본 측정 전 구간에서 Replica OFF를 반복 확인한다. A 중 Replica에 SQL·cgroup 조회를 보내거나 자동으로 다시 시작하지 않는다.
4. **B 슬롯은 Replica ON·복제 스레드 정상·오류 0을 확인**한 뒤 앱을 준비한다. 두 arm 모두 앱 health, 세션·라우팅 smoke, 실제 JVM 설정, 공통 입력 해시를 확인한다.
5. 600초 워밍업을 한 번 실행한다. 요청 오류·관측 coverage·입력 불변·JIT 기준을 통과하지 못하면 추가 워밍업 없이 중단·복구한다. 통과하면 앱을 유지한 채 부하를 중단한다. B는 워밍업 쓰기에 대해 GTID catch-up을 확인한 후 유휴 안정화를 시작한다. A는 Replica가 꺼진 상태로 Primary 유휴 안정화만 수행한다.
6. 유휴 안정화와 해당 arm의 DB 실행 상태를 다시 확인하고 900초 본 측정을 시작한다. 시작 시각은 JTL의 최소 요청 시작 timestamp로 고정한다. 실행 중 DB 토폴로지·자원·설정을 바꾸지 않는다.
7. 본 측정 종료 후 결과와 최종 표본을 보존한다. 다음 슬롯을 준비하기 전에 태스크 앱의 쓰기 발생을 종료한다. A에서는 이때 비로소 Replica를 다시 시작한다. 그 뒤 B와 공통으로 현재 Primary GTID에 대한 catch-up·복제 health를 확인하고, 다음 슬롯 전 유휴 상태를 확인한다. 컨테이너 재기동에 따른 Replica counter reset은 측정 밖에서 기록하고 다음 슬롯의 첫 counter를 새 기준으로 잡는다.
8. 다음 슬롯은 앞선 미복제 backlog가 없는 상태에서 시작한다. 마지막 슬롯 후에도 catch-up을 확인하고 전체 복구·독립 검증을 수행한다.

A를 측정하는 동안 쌓인 Replica backlog는 의도된 중지에 따른 것이다. A 종료 후 동기화 시간은 **실험 전환 비용**으로 따로 기록하며, A가 운영 중 복제 lag를 발생시켰다고 해석하지 않는다. B의 부하 종료 후 catch-up은 B에서 누적된 복제 지연의 회복으로 구분한다. 두 시간의 개선율을 계산하지 않는다.

GTID 확인 단계의 대기 시간과 마지막 HTTP 응답부터 GTID 확인까지의 전체 경과를 구분한다. 후자는 저장한 마지막 응답 시각과 GTID 통과 기록 시각으로 계산한다. GTID는 약 15초 주기로 확인하므로 실제 적용 완료 순간보다 늦게 관측될 수 있다. 각 검사에서 현재 Primary의 GTID가 Replica에 포함되는지와 복제 health를 확인한다. 고정된 시작 GTID 하나만 검사하는 방식은 아니며, GTID 포함 확인을 행 전체 내용 checksum이나 측정 중 read-your-writes 검증으로 표현하지 않는다.

## 유휴 안정화와 안전 기준

기존 안정화 기준을 유지한다. 15초 간격으로 수집하며 최소 120초, 최대 600초를 기다린다. 마지막 약 60초 관측으로 아래 기준을 계산하고 연속 2회 통과해야 한다. A는 실행 중인 Primary만, B는 두 DB 모두 판정한다.

| 항목 | 기준 |
|---|---|
| CPU 평균 | 1코어 기준 10% 이하 |
| 디스크 read + write 평균 | 1 MiB/s 이하 |
| 앞·뒤 30초 CPU 평균 차이 절댓값 | 5%p 이하 |
| 앞·뒤 30초 I/O 평균 차이 절댓값 | 0.25 MiB/s 이하 |
| 관측 간격 | 개별 최대 35초, 마지막 4개 간격 합 59~75초 |
| GTID catch-up | 단계당 최대 1,800초 |

이는 유휴 활동에 대한 운영상 기준이며 캐시나 JVM의 완전한 평형을 증명하지 않는다. 시작 시 물리 메모리 여유 4 GiB 이상을 요구한다. 실행 중 물리 여유 1 GiB 미만 또는 커밋 여유 2 GiB 미만이면 중단한다. 모니터링과 부하 프로세스까지 포함한 호스트 표본을 보존한다.

00:00·04:00 KST의 앱 예약 작업과 겹치지 않도록 각 슬롯 진입에 **200분 여유의 cron guard**를 사용한다. 워밍업 10분·본 측정 15분 외에도 단계별 GTID 대기와 유휴 안정화·복구 시간이 필요하므로 기존 100분 기준을 그대로 사용하지 않는다. 진입할 시간이 부족하면 태스크 앱이 없는 상태에서 경계를 넘긴 후 시작한다. 200분은 추가 부하 재시도를 허용하는 예산이 아니라 슬롯의 대기·복구 여유다.

## 측정 유효성과 복제 안정성

HTTP 대표 구간은 마지막 120초 `[780,900)`, TPS 정상상태 참조 구간은 `[180,300)`이다. 본 측정 전체와 1분별 추이도 보존한다. 워밍업과 본 측정을 섞지 않는다.

HTTP 비교에 포함하려면 본 측정 종료 코드 정상, 전체 parent 요청 오류·redirect child 오류·invalid row 0, 관측 coverage 충족, 입력·컨테이너 상태 불변, 두 앱 JIT 통과, TPS STEADY가 필요하다. 기존 JIT 기준은 마지막 관측의 약 120초 compilation 누적 증가량을 마지막 누적값으로 나눈 비율 2% 이하다. 두 앱 각각 counter reset·표본 공백·오래된 마지막 표본이 없어야 한다.

기존 TPS 판정 함수를 유지한다. tail과 참조 구간의 TPS 차이율, tail 뒤 60초와 앞 60초의 TPS 차이율이 각각 **−5% 이상 +3% 이하**일 때 STEADY다. 이 비대칭 허용 구간은 기존 사전 기준이며 새 결과에 맞춰 조정하지 않는다. TPS STEADY를 응답시간이나 복제 지연의 안정성이라고 표현하지 않는다. 응답시간은 1분별 평균·분위수와 마지막 두 60초의 변동을 함께 제시한다.

B 복제 안정성은 HTTP 유효성과 별도로 마지막 5분 `[600,900)`에서 판정한다.

| lag 항목 | 안정 기준 |
|---|---|
| p95 | 2초 이하 |
| 최대 | 5초 이하 |
| 종료 표본 | 2초 이하 |
| 선형 기울기 절댓값 | 0.2초/분 이하 |
| 첫·끝 1분 평균 차이 절댓값 | 1초 이하 |
| 표본·health | 최소 18표본, 기존 간격·경계 coverage 기준 충족, 복제 스레드 정상·오류 0 |

다섯 수치 기준을 모두 만족해야 STABLE이다. 표본이 유효하지만 기준을 넘으면 UNSTABLE, 관측 부족이나 health 문제가 있으면 판정 불가·실패로 구분한다. **A의 Replica CPU·lag·복제 health는 `N/A — Replica stopped`**로 기록한다. 꺼진 DB를 lag 0이나 복제 안정성 통과로 표시하지 않는다. Prometheus의 이전 표본이 조회되더라도 A의 현재 값으로 재사용하지 않는다.

이 lag 기준은 반복 비교를 위한 기존 진단 기준이며 제품 freshness SLO나 3초 Sticky의 보장 범위가 아니다. 세 번 중 일부만 통과하면 회차별 결과를 그대로 제시하며 ‘복제 안정성 확보’라고 결론 내리지 않는다.

## 집계·그래프·해석

- 예정된 6개 슬롯의 원시 결과·유효 여부·제외 이유를 모두 보존한다. A/B 각각 3회가 유효하면 TPS·평균·p50/p95/p99의 **중앙값과 최솟값–최댓값**을 비교한다. 3회씩 충족하지 못하면 확보한 회차의 관측값을 공개하되 확정 비교 기준 미달을 표시한다. 중단 시에는 실제 실행한 슬롯 전체와 미실행 슬롯을 구분한다. 퍼센타일의 중앙값은 개별 실행 퍼센타일의 중앙값이며 요청을 모두 합친 퍼센타일과 다르다.
- 대표 Grafana 캡처는 각 arm의 TPS 중앙값에 가장 가까운 유효 회차를 선택한다. 동률이면 사전에 정한 이름순으로 선택하고, 모든 회차 수치는 별도 표로 공개한다. 가장 유리한 응답시간이나 lag 화면을 골라 대표라고 하지 않는다.
- Grafana는 기존 다크 1000×500 단일 패널 양식으로 고정 시간 전체 900초를 캡처한다. 요청 시간 분포·컨테이너 CPU·B lag를 제시하고 A lag는 측정 대상이 아님을 명시한다. 캡처 요청의 KST 시간 범위·대시보드·패널·해시를 보존한다. 기존 CPU 패널이 임시 App 이름을 제외하면 DB CPU 캡처로 설명하거나, 쿼리를 바꿨다는 사실을 명시한 별도 공통 패널로 양쪽을 동일하게 캡처한다.
- JMeter의 완료 parent 요청을 요청 시작 timestamp로 구간에 배정한다. redirect child는 중복 집계에서 제외하되 오류를 보존한다. Grafana 앱별 percentile·rate와 JMeter 전체 요청 집계는 정의가 다르므로 수치가 같아야 한다고 가정하지 않는다.
- HTTP 라벨 기준 GET·내용 변경 POST·로그인을 구분해 완료량과 응답시간을 제시한다. GET에도 조회수 쓰기 등이 있고 POST 수는 SQL·commit 수가 아니므로 DB 읽기·쓰기 작업 수로 바꾸어 부르지 않는다. SELECT QPS·Primary/Replica CPU와 함께 읽기 이동을 확인한다.
- 500 VUser는 closed-loop 동시 사용자 수를 고정할 뿐 요청·쓰기 도착률을 고정하지 않는다. TPS와 쓰기 요청량이 달라진 상태의 lag를 동일 입력률에서의 순수 복제 처리 능력 차이로 해석하지 않는다.
- A/B 중앙값 차이는 이 통제된 도입 구성의 반복 관측으로 제시한다. 단회였던 9월 8일 안정화나 9월 9일 0.5/1.5 결과와 바로 나눈 수치를 이번 비교의 개선율로 사용하지 않는다. 시간·데이터 누적·공유 호스트의 한계를 남긴다.
- B의 HTTP가 개선돼도 lag가 계속 늘면 ‘읽기 분산으로 응답은 개선됐으나 500 VUser의 복제 최신성은 확보하지 못했다’고 구분한다. 개선이 없거나 일부 지표가 악화돼도 그대로 기록한다.

## 중복 실행 방지와 복구

신규 캠페인 디렉터리는 이미 존재하면 시작을 거부한다. 실행 중 상태·owner label·활성 JMeter 프로세스를 확인해 동일 캠페인을 중복 시작하지 않는다. 실패한 슬롯 이름을 재사용하지 않으며 입력·이미지·기존 결과의 해시를 보존한다. 외부 블로그와 포트폴리오 수정은 측정·분석·복구 확인 후 결과에 근거해 진행한다.

예외·요청 중단·유효성 실패에도 태스크 소유 부하와 임시 컨테이너만 종료한다. 중지했던 원래 Replica의 정확한 ID를 다시 시작하고, 원래 DB 자원·설정과 복제 상태를 복구한다. Replica 재설정·재생성·초기화는 하지 않는다. GTID catch-up 후 원래 앱과 관련 서비스를 원래 실행 상태로 돌린다. Grafana·Prometheus·renderer를 포함해 시작 전 journal과 ID·실행 상태·CPU·메모리·restart policy를 비교한다.

최종 검증은 별도 호출로 앱 health, 복제 스레드·오류, GTID 포함 관계, 양 DB의 주요 테이블 행 수, 임시 컨테이너 잔존 여부를 확인한다. 행 수 확인은 전체 내용 검증이 아니다. 복구 실패를 숨긴 채 캠페인 완료라고 보고하지 않는다.

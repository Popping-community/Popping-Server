# Replica 도입 재실험 — 고정 20분 워밍업 사전 계획

> 최신 완료: 고정 20분 워밍업 캠페인에서 A·B 각 3회 유효 본측정과 원복을 완료했다. TPS 536.700→531.683/s, 평균 53.573→57.244ms이며 B 복제 지연은 모두 불안정했다. [최종 보고서](replica-warm20-20260910.md). 아래 내용은 당시 계획 또는 이전 결과로 보존한다.

2026-09-10 사용자가 재실험을 요청했다. 낮 캠페인의 5A 워밍업 JIT 기준 초과를 반영해 **워밍업 준비 절차만 새로 정의**한다. 이전 원본과 하네스는 보존하며 새 하네스 `.tmp/replica-adoption-warm20/`, 새 캠페인 `replica-20260910-warm20-01`을 사용한다. 기존 부분 결과를 반복수에 합치지 않는다.

## 변경한 준비 절차

- 500 VUser·ramp 60초의 동일 워크로드로 **1200초 연속 워밍업 1회**를 수행한다. 1200초가 고정 길이이자 상한이며, 조기 통과해도 끝까지 진행한다. 하네스의 프로세스 종료 여유 180초는 추가 부하 목표 시간이 아니다.
- JIT 확인 시점은 최초 요청 시작 기준 600·900·1080·1200초다. 600·900초 판정은 진단용이며, **1080초와 1200초의 두 판정에서 app-1·app-2 모두 통과**해야 본측정을 준비한다.
- 각 JIT 판정은 기존 함수 그대로 최근 약 120초의 누적 컴파일 시간 증가분을 마지막 누적값으로 나눈 비율이 **0~2%**인지 확인한다. 관측 수·신선도·간격·counter reset 검증도 유지한다. 이 값은 CPU 사용률이 아니며 전체 캐시/JVM 평형의 증명도 아니다.
- 한 번의 고정 워밍업이 실패하면 캠페인을 중단하고 복구한다. 자동 재시도·추가 워밍업·사후 임계값 변경은 없다. 이전의 실패한 600초 기록을 새 절차의 성공으로 재분류하지 않는다.
- 워밍업을 마친 뒤 기존과 같이 GTID 추격·유휴 상태를 확인하고 900초 본측정을 진행한다. 본측정의 JIT 판정과 마지막 120초 `[780,900)` 성능 계산은 바꾸지 않는다.

## 유지하는 비교 조건

| 항목 | A | B |
|---|---|---|
| Primary | 1 CPU / 1 GiB | 1 CPU / 1 GiB |
| Replica | 컨테이너 OFF | 1 CPU / 1 GiB |
| 읽기 풀 | Primary | Replica, Sticky 적용 시 Primary 가능 |
| 쓰기 풀 | Primary | Primary |
| lag | N/A | 별도 안정성 평가 |

공통: App 2대 각 2 CPU / 2 GiB·실제 최대 힙 240 MiB, HAProxy, Write 20 / Read 30, Sticky ON 3초, Redis 세션 OFF. Replica worker 2개·커밋 순서 유지·내구성 1/1. 500 VUser(300/150/5/5/40), ramp 60초, ABBAAB 각 3회다. 이미지 `sha256:cb215e007e159b821a47a46d39214e721926288ed8828147444b08d2f8d769e9`와 생산 코드를 유지한다.

쓰기 데이터는 누적하며 초기화하지 않는다. 슬롯마다 같은 smoke → 워밍업 → GTID/유휴 → 본측정 → 앱 제거·복제 추격 순서를 적용한다. JMeter와 Docker는 호스트를 공유한다. CPU 재배분 실험이 아니며, B는 Replica 자원·복제 작업·라우팅이 함께 추가되는 구성 비교다.

HTTP/coverage/입력/복제 오류/자원·프로세스 안전 기준 실패는 중단·원복한다. 본측정의 JIT/TPS만 미달하면 원본과 제외 사유를 남기고 정해진 슬롯을 계속한다. B lag UNSTABLE은 HTTP 측정 제외나 재시도 사유가 아니다. 비교 가능 조건은 유효한 A·B 각 3회다. 부족하면 미달을 그대로 보고한다.

기존 메모리·자정/04시 예약 작업 회피·컨테이너 소유권·정확한 ID·DB 재시작 방지·로그 보존·원복 검증을 유지한다. 완료 후 원래 전체 25개 컨테이너 상태/자원/이미지, 복제·GTID·행 수·앱 health·동결 입력을 독립 검증한다. 측정 중 대량 JTL 분석·렌더링·추가 부하를 실행하지 않으며 상태 확인은 약 10분 및 주요 단계·오류 중심이다.

## 사전 구현 검증

기존 하네스는 31개 원본 파일 hash로 추가 보존했다. 새 warmup JMX는 5개 ThreadGroup의 duration 600→1200만 바꾸었고 그 외 모든 바이트가 같다. smoke·measure JMX는 원본과 완전히 같다. 새 확인 함수·1200초 coverage·누락 JVM·관측 간격·reset·이전 실제 실패 원본·기존 격리/복구/분석 회귀를 포함한 **51개 테스트가 통과**했다. 서비스나 부하를 실행하는 테스트는 아니다.

## 비교와 해석

완료 후 [직전 낮 재실험](replica-adoption-rerun-20260910.md)의 각 2회와 초기 원본 재계산을 함께 대조한다. 이번 워밍업 변경 전후에도 데이터가 누적되고 실행 시간이 다르므로 방법 하나의 인과 효과로 단정하지 않는다. 보고서에는 전체 회차와 제외 사유, 중앙값·범위, HTTP 성능과 복제 안정성을 구분해 남긴다. 기존 문서·이미지를 보존하며 새 결과와 실제 Grafana 캡처를 추가한다.

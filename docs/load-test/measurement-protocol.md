# 부하테스트 측정 프로토콜

이 저장소에서 성능 개선의 before/after를 측정할 때 지키는 규칙과 절차. **수치를 인용하기 전에 이 문서의 규칙을 통과했는지 먼저 확인한다.**

---

## 왜 이 문서가 생겼는가

2026-08-12~13에 750 vuser / 600초 조건으로 4개의 런을 측정했다. **비교 가능한 쌍이 하나도 없었다.**

| 런 | 이미지 | 판정 | 문제 |
|---|---|---|---|
| 16:57 베이스라인 | 구 코드(3개월 전 빌드) | 폐기 | 호스트 커밋 여유 1.45GB에서 측정 — 오염 |
| run4 | 구 코드 | 폐기 | 재현 실패(+20%), 코드가 최신이 아님 |
| rebuild | SVG 이전 | WARMING | 종료 시점까지 처리량이 계속 상승 |
| svg run1 | SVG 적용 | WARMING | 상동, 정도가 더 심함(+23.7%) |
| svg run2 | SVG 적용 | STEADY | 유효하나 **비교 상대가 없음** |

각각 다른 이유로 무효였고, 공통점은 **측정하기 전에 무엇이 같아야 하는지를 정하지 않았다는 것**이다. 아래 규칙은 전부 실제로 한 번씩 데인 항목이다.

---

## 규칙 1 — 컨테이너를 재생성한 뒤 첫 런은 버린다

`docker compose up --force-recreate`는 JVM을 콜드 상태로 되돌린다. 앱 컨테이너가 CPU 상한(2코어)에 붙어 있으면 C2 컴파일러 스레드가 요청 스레드와 CPU를 두고 경쟁하기 때문에, **워밍업이 600초 안에 끝나지 않는다.**

근거가 되는 실측 — 동일 이미지 · 동일 조건, 차이는 앞선 부하 통과 여부뿐:

| | run1 (콜드) | run2 (직전 런으로 데워짐) |
|---|---|---|
| TPS (마지막 120초) | 486.7 | **662.5 (+36%)** |
| avg / p99 | 659ms / 2,589ms | 258ms / 977ms |
| App1/App2 CPU (한도 200%) | 205~220% (포화) | 173~201% (여유) |
| 캐시 히트율 | 71.8% | **68.1%** |

CPU를 **덜** 쓰면서 36% 더 처리했고 캐시 히트율은 오히려 낮았다. 애플리케이션 캐시로는 설명되지 않는다. JIT 워밍업이 가장 유력하지만 buffer pool·OS 캐시·커넥션 풀 상태도 후보이고, 이 지표들만으로 원인을 하나로 확정하지는 못한다.

**원인 특정은 필요하지 않다.** 확정된 것은 "시작 상태가 다르면 36% 차이가 난다"는 사실이고, 이 36%는 어떤 코드 최적화보다도 크다. 즉 **워밍업을 통제하지 않으면 다른 모든 비교가 무의미해진다.**

→ `run-ab.sh`가 워밍업 패스를 먼저 돌리고 결과를 버린다. 다음 단계로 넘어갈지는 `jvm_compilation_time_ms_total`의 증가가 멈췄는지로 판정한다(마지막 120초 증가분이 누적의 2% 이하). 미달이면 워밍업 패스를 한 번 더 돈다(최대 3회).

이 JIT 판정은 **워밍업 완료의 증명이 아니라 사전 필터**다. JIT 활동이 잦아들었다는 것만 말해줄 뿐 DB·OS 캐시까지 데워졌는지는 말해주지 않는다. 최종 합격 판정은 규칙 3(본 측정의 STEADY 여부)이며, JIT 게이트를 통과하고도 STEADY에서 떨어지면 그 런은 버린다.

## 규칙 2 — 비교 창은 마지막 120초다

전 구간 평균은 램프업 구간(60초)과 워밍업 구간을 섞는다. 같은 런을 어떤 창으로 보느냐에 따라 결론이 뒤집힌다.

```bash
python docs/load-test/analyze-jtl.py <run.jtl> 480   # 600초 런의 마지막 120초
```

실제로 과거에 "실행 간 분산 20%"라고 판단했던 것은 실체가 아니라 램프 구간을 평균에 섞은 산물이었다.

마지막 120초라고 해서 저절로 대표성을 갖는 것은 아니다. **규칙 3의 STEADY 판정을 통과한 런에 한해** 이 창의 값을 쓴다. 전 구간 평균도 기록은 하되 참고값으로만 다룬다.

## 규칙 3 — STEADY 판정을 통과하지 못한 런은 폐기한다

```bash
python docs/load-test/check-steady-state.py <run.jtl>
```

판정 기준: **꼬리 120초의 처리량**을 **180~300초 구간**과 비교한다.

| 판정 | 조건 | 처리 |
|---|---|---|
| STEADY | 차이 ≤ +3%, 꼬리 내부 기울기도 ≤ +3% | 사용 가능 |
| MARGINAL | +3% 초과 ~ +5% 이하 | 주의해서 사용 |
| WARMING | +5% 초과 (또는 꼬리 내부 기울기 +5% 초과) | **폐기** — 용량이 아니라 워밍업을 잰 것 |
| DEGRADING | −5% 미만 | 폐기 — 무언가 무너진 것 |

꼬리 내부 기울기를 따로 보는 이유는, 창 대 창 비교만으로는 "초반에 오르고 평평해진 런"과 "끝까지 오르는 런"을 구분하지 못하기 때문이다.

합격/불합격 판정은 **처리량만** 본다. 스레드 수가 고정된 closed-loop 테스트라 평균 응답시간은 처리량과 거의 역수 관계이고, 둘 다 규칙에 넣으면 같은 신호를 두 번 세게 된다. 단 이건 평균 수준의 이야기다. **p99와 에러율은 처리량으로 대체되지 않으므로** 판정에서 빼되 반드시 함께 기록하고 본다.

## 규칙 4 — 두 arm의 시작 조건을 맞춘다

`run-ab.sh`가 강제하는 것들:

| 조건 | 이유 |
|---|---|
| 복제 지연 0에서 시작 | 수백 초 밀린 replica는 CPU를 backlog 적용에 쓴다. 과거 런들은 lag이 각각 0~32초 / 104~239초 / 288~447초로 서로 달랐다 |
| 앱 서비스 2개가 **같은 이미지 태그** | `sed` 치환 후 2줄인지 검증 |
| 캐시 카운터 pre/post 스냅샷 | 카운터가 누적값이라, 워밍업 패스가 섞인 상태에서는 차분 없이는 히트율을 못 구한다 |
| 실행 jmx의 sha256 기록 | 실행되는 `C:\apache-jmeter-5.6.3\bin\popping-load-test.jmx`는 저장소 사본과 다르다(ramp 60 vs 120). 다르면 경고를 남긴다 |
| git HEAD · 컨테이너 image ID · JMeter 힙 설정 기록 | 나중에 "같은 실험이었나"를 확인할 수 있는 유일한 근거 |

## 규칙 5 — 복제 지연을 성공 지표로 쓰지 않는다

`Seconds_Behind_Source`는 다중 스레드 replica에서 최신 커밋 위치를 반영하지 않는다(MySQL 8.4). 관찰용으로는 기록하되, **개선 여부의 판정 지표로는 쓰지 않는다.** 필요하면 GTID 기반으로 `retrieved − executed`(applier backlog)를 보고, 값 자체보다 **기울기가 양수인지 / 유계인지**를 본다.

또한 MySQL 8.4에서 컬럼명이 바뀌어 `mysql_slave_status_seconds_behind_master`는 존재하지 않는다. `..._seconds_behind_source`를 쓴다.

## 규칙 6 — arm 하나로 결론내지 않는다

`run-ab.sh`는 한 번에 arm 하나를 돈다. before/after를 각 1회씩만 돌리면 코드 변경의 효과와 런 간 드리프트를 분리할 수 없다. **교대로(A B A B) 돌리고 중앙값으로 비교한다.** 사전에 "몇 % 이상이면 채택"을 정해두고 시작한다(예: 3%).

## 부록 A — 실행 절차

### 사전 점검

```bash
docker info --format '{{.ServerVersion}}'            # 데몬 살아있는지
docker compose -f C:/monitoring/docker-compose.yml up -d   # Prometheus/Grafana (레포 밖)
curl -s 'http://localhost:9090/api/v1/targets?state=active'  # 6개 타깃 UP
```

호스트 커밋 여유도 본다. JMeter 750스레드는 네이티브 스택만으로 수백 MB를 쓰기 때문에, 커밋 여유가 부족하면 힙과 무관하게 네이티브 OOM으로 죽는다(실제 발생 이력 있음).

```powershell
$os = Get-CimInstance Win32_OperatingSystem
"CommitFree_GB = {0:N1}" -f ($os.FreeVirtualMemory/1MB)
```

### arm 실행

```bash
bash docs/load-test/run-ab.sh <런이름> <이미지태그>

# 예: before/after 교대
bash docs/load-test/run-ab.sh stage1-before-1 stage1-20260812
bash docs/load-test/run-ab.sh stage1-after-1  stage1-svg-20260813
bash docs/load-test/run-ab.sh stage1-before-2 stage1-20260812
bash docs/load-test/run-ab.sh stage1-after-2  stage1-svg-20260813
```

arm 1회 = 워밍업 600초 + 복제 배출 대기 + 본 측정 600초 ≈ **27~45분**. 종료 코드는 0(사용 가능) / 1(셋업 실패) / 2(돌긴 했으나 비교 불가).

환경 변수로 조절 가능: `WARMUP_SKIP=1`(이미 데워진 JVM 재사용), `WARMUP_MAX_PASSES`, `JIT_SETTLED_RATIO`, `LAG_WAIT_TRIES_POST_WARMUP`.

### 분석

```bash
python docs/load-test/check-steady-state.py <A.jtl> <B.jtl>   # 먼저 판정
python docs/load-test/analyze-jtl.py <A.jtl> 480              # 통과한 것만 비교
```

## 부록 C — 2026-08-14 적용 사례 (SVG 스프라이트)

이 프로토콜로 처음 돌린 실험. before/after 교대 3회씩, **6런 전부 STEADY / 에러 0%**.

| | r1 | r2 | r3 | 평균 |
|---|---|---|---|---|
| before TPS | 606.3 | 631.1 | 613.1 | 616.8 |
| after TPS | 646.4 | 650.5 | 616.9 | **637.9 (+3.4%)** |

통제 확인: 캐시 히트율 66.8~67.2%, 종료 시점 복제 지연 517~542초, 워밍업 패스 수 6런 모두 2회
(JIT 증가율 1패스 0.176~0.190 → 2패스 0.005~0.010).

**판정: 미확정.** 6개 값을 두 그룹으로 나누는 20가지 중 관측만큼 치우친 배치가 2가지 → 단측 **p = 0.10**.
after r3(616.9)이 before r2(631.1) 아래로 내려와 분리가 깨졌다.

이 실험에서 얻은 교훈 3가지:

1. **2쌍까지는 완전 분리였다.** 거기서 멈췄다면 "+4.8% 개선"으로 결론냈을 것이다. 규칙 6이 실제로 값을 했다.
2. **before arm 자체가 4.1% 흔들린다**(606.3~631.1). 이 환경에서 3% 수준의 효과는 검출할 수 없다는 뜻이다.
   효과 크기가 이보다 작을 것으로 예상되는 최적화는 이 부하 모델로 검증하지 말 것.
3. **3쌍째 두 런 모두 꼬리가 하락했다**(-4.0%, -3.8%). 앞선 4런에는 없던 현상이고 **원인은 미규명이다.**
   배제된 것: JMeter 클라이언트 포화(마지막 120초 CPU 0.85~1.01코어 / 호스트 12코어).
   약한 후보: 쓰기 누적 — 실측 결과 하루 18패스에서 약 6만 행으로 전체 620만 행의 1%에 그친다.
   남은 후보: replica 상태(버퍼 풀·purge), InnoDB history list, 호스트 상태.
   **순서 편향도 있다** — A B A B A B 순서에서는 after arm이 항상 한 칸 늦게 실행되므로,
   시간에 따른 하락이 실재한다면 측정된 +3.4%는 과소평가다. 다음 측정은 A B B A로 상쇄할 것.

## 부록 D — 알려진 한계

- **DB를 arm 간에 초기화하지 않는다.** 쓰기가 누적된다 — 실측 arm당 약 1만 행(패스당 약 3,500행).
  2026-08-12 기준 대비 post +40,316 / comment +40,195 / likes +36으로, 전체 620만 행의 1% 수준이다.
  좋아요는 add/remove가 짝을 이뤄 사실상 늘지 않는다. 미미하지만 0은 아니고, 되돌리는 절차도 없다.
- **복제 지연 0 대기 시간이 arm마다 다르다.** 빠른 arm이 더 많은 쓰기를 만들어 backlog가 크기 때문. 안 기다리는 쪽이 더 큰 왜곡이라 감수한다.
- **JMeter가 같은 호스트에서 돈다.** 클라이언트 포화 여부는 `metrics.csv`의 `jmeter_cpu_s`를 미분해서 확인한다(코어 수에 근접하면 부하 생성기가 병목).
- **실행 jmx가 저장소 밖에 있다.** 해시로 감지만 하고 자동 동기화는 하지 않는다.

## 해석과 이전 결과 비교

`03`은 슬롯별 워밍업 전에는 동기화했지만 워밍업 직후에는 기다리지 않았다. 당시 A/B 중앙값은 TPS 554.125/537.875, 평균 18.876/44.771ms였다. 이번 `05`는 워밍업 후 동기화를 추가해도 중앙값 기준 성능 저하가 남았다. 워밍업 backlog만으로 `03`의 저하를 설명할 수 없다. 다만 두 캠페인 사이의 변화량을 동기화 대기만의 인과 효과로 단정하지 않는다.

B는 본 측정 중 다시 복제 지연이 커졌고 Replica CPU는 tail 평균 약 96~100%였다. 읽기와 복제 적용의 자원 경합 가설을 지지한다. A에서도 복제 지연이 관측돼 복제 자체의 처리 여유도 제한적이다. CPU throttling과 디스크 I/O의 기여도는 이 자료만으로 분리할 수 없다.

6B는 다른 B보다 빠르며 1A보다도 평균 응답시간이 짧다. 따라서 모든 B가 모든 A보다 느렸다고 표현하지 않는다. STEADY는 처리량 판정이며 복제 지연 안정성의 보장이 아니다. JIT 기준은 본 측정 6회에서 통과했지만, 최대 약 277초의 대기가 캐시·JVM 상태에 미치는 모든 효과를 배제하지는 못한다.

쓰기 데이터는 순서대로 누적했고 DB를 초기화하지 않았다. JMeter와 Docker는 호스트를 공유한다. 과거 단일 관측의 `42ms -> 11ms` 개선은 당시 기록으로 유지하되, 실행 메타데이터가 부족하므로 현재 결과와 차이가 난 정확한 원인은 미확정이다.

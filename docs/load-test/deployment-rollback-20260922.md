# 이전 이미지 재생성을 통한 중단 후 복구

2026-09-22. 정상 V1→V2 교체 후 유일하게 서비스하던 V2를 강제 종료하고,
보관한 정확한 V1 이미지로 복귀했다. **중단 후 복구** 실험이며 무중단 롤백은 아니다.
실험은 `popping-drain-check-rollback-20260922`와 loopback196xx에서 수행했다.

## 결정과 구현

기존 admission 도구는 정상 old 서버가 UP이라는 조건을 요구한다. 전부 중단된
상황에서 그 조건을 우회하지 않고 `scripts/deployment/recover_server.py`를 추가했다.

복귀 대상은 MAINT여야 한다. 실패한 V2의 정확한 컨테이너가 exited임을 확인하고,
해당 프록시 슬롯도 MAINT로 고정한다. DOWN만 두면 재시작이나 주소 재사용 후
다시 유입될 여지가 있어 이를 허용하지 않는다.

복귀 대상의 전체 컨테이너 ID, Compose project/service label, 기대 이미지 ID,
running 상태, 시작 시각, 프록시 주소, loopback으로 연결한 business port의 실제
바인딩을 대조한다. 실패 컨테이너도 기대 이미지·시작 시각·exited를 재확인한다.
readiness와 기존 Redis SESSION을 사용한 보호 GET·버전 marker를 3회 연속 확인한
후 신원을 다시 검사하고 ready로 바꾼다. HAProxy UP과 직전 L7 성공 이후에도
신원을 확인한다. ready 시도 후 실패하면 MAINT 재설정·확인을 요구하고, 확인되지
않으면 `recovered=null`로 남긴다.

이 도구 자체는 컨테이너 생성, 장애 자동 감지, DB migration, 복귀 후 지속 관측을
하지 않는다. 실험 드라이버가 단일 제어자로 이를 수행한다. 개별 네트워크·Docker
호출 timeout이 따로 있어 polling deadline은 엄격한 전체 시간 제한이 아니다.

## 실제 검증 순서

1. V1에서 로그인한 SESSION을 한 번만 발급했다.
2. V2 후보 투입과 프록시 V2 확인 후 V1을 드레인·SIGTERM 종료했다.
3. V2에서 댓글을 한 번 쓰고 HTTP 200·DB ID·부모 count=1을 확인했다.
4. 정확한 격리 V2 컨테이너에 SIGKILL을 보내 exit137와 HAProxy DOWN을 확인했다.
   이후 V2를 MAINT로 고정했다. 진행 중 쓰기를 강제 중단한 실험은 아니다.
5. 보관한 V1 이미지 ID로 old를 재생성했다. 새 컨테이너와 IP를 확인하고 MAINT
   상태에서 프록시 주소를 설정했다. 이번에도 IP 자체는 이전과 같았다.
6. 기대 버전을 일부러 V3로 지정했다. readiness200/UP·인증 GET200이어도 marker
   불일치로 거절, ready 호출 없이 MAINT를 유지하고 프록시 503을 확인했다.
7. V1 marker로 재시도해 투입한 후 프록시의 실제 보호 본문·V1·old 응답을 확인했다.
8. 같은 SESSION으로 V2가 쓴 댓글을 V1에서 읽고, V1에서 새 댓글을 한 번 더 썼다.

V1·V2는 이전 단계에서 보관한 불변 이미지다. JAR의 보호 페이지 marker만 다르고
클래스·라이브러리·스키마는 같다. 기능·스키마·세션 직렬화 역호환까지 검증한 것은 아니다.

## 결과와 중단 관측

| 관측 | 결과 |
|---|---:|
| 주기적 보호 GET/전송 오류 기록 | 111건 |
| HTTP 200 | 18건: V2 4건, 복귀 V1 14건 |
| HTTP 503 | 92건 |
| 전송 오류 | TimeoutError 1건 |
| 복귀 후 별도 보호 GET | 12/12 정상, V1·old·보호 본문 |
| V2 댓글 / 복귀 V1 댓글 | ID 1 / ID 2 |
| 최종 해당 게시글 DB 댓글 행 / 부모 count | 2개 / 2 |

V1이 V2 댓글의 ID와 `written-on-v2` 내용을 실제 HTTP로 읽는 것까지 확인했다.
재로그인·쓰기 자동 재전송은 없었다. V2는 마지막에도 동일한 exited 컨테이너로
남았고 프록시 MAINT가 유지됐다.

장애 주입 호출 시작을 0초로 한 호스트 관측:

| 이벤트 | 경과 |
|---|---:|
| V2 MAINT 및 직접 프록시 503 확인, V1 재생성 시작 | 0.680초 |
| V1 직접 readiness 확인 | 27.108초 |
| 의도적 잘못된 marker 검사 거절 | 31.808초 |
| 정상 V1 복귀 게이트 반환 | 33.715초 |
| 주기적 관측 중 첫 V1 성공 요청의 **시작 시각** | 33.785초 |
| 별도 V1 보호 GET 12건 완료 확인 | 34.774초 |

이 수치는 로컬 단일 실험이며 의도적 잘못된 marker 검사 지연이 포함된다.
운영 RTO나 일반적인 cold start 성능으로 해석하지 않는다. 샘플러는 응답 후
0.25초를 기다리므로 고정률 부하가 아니다. timeout은 다음 샘플도 늦춘다.
첫 성공 요청의 시작 시각은 응답 완료 시각과 다르다.

실행 당시 전송 오류 한 건의 `sent_at`은 실제 전송 시각이 아니라 예외를 받은
시각이었다. 원본을 고치지 않고 이 한계를 남겼다. 후속 코드에서는 요청 시작과
오류 관측 시각을 분리했으며 그 변경으로 실험을 다시 실행하지는 않았다.

## 검토와 검증 상태

- 배포 도구 단위 테스트 23개 통과: 기존 16개 + 복귀 7개.
- 독립 리뷰에서 wrong-marker의 `all([])` 허위 통과 가능성을 발견해 timeout
  reason·빈 배열 금지·readiness health_up을 추가했다. 저장된 실제 5회 검사에
  강화한 조건을 적용해 통과했으며 실패 유형이 marker 불일치임을 확인했다.
- 이후 fixture의 포트 치환도 포트 부분만 바꾸도록 좁혔다. 실행에 사용한 이미지
  해시는 기존 치환 대상 문자열을 포함하지 않아 이번 결과에는 영향이 없었다.
- 앱 Java·클래스 변경이 없어 Gradle 전체 테스트는 재실행하지 않았다. 앞 단계의
  175개 통과를 이번 실행 결과로 재계산하지 않는다.
- 실험 컨테이너 5개 정리, 기존 Popping 10개의 실행 중 ID 보존, 임시 SESSION 삭제.
  이전 이미지 두 개는 재현용으로 유지했다.

## 해석과 다음 선택

이전 이미지가 있어도 이미 종료한 프로세스를 다시 시작하고 검증하는 동안
중단은 발생했다. 짧은 rollback 시간을 원하면 이전 인스턴스를 일정 기간
트래픽에서만 제외한 채 유지하는 대안을 비교할 수 있다. 그 경우 메모리·CPU
점유와 버전·DB 호환성 관리 비용을 함께 부담한다. 아직 이 대안을 측정하지 않았다.

이번 결과는 자동 장애 대응, 무중단 롤백, 진행 쓰기 보존, 호스트 장애 HA,
스키마 rollback을 증명하지 않는다. 원격 배포·이미지 push·commit도 수행하지 않았다.

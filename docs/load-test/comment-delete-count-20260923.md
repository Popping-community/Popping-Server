# 댓글 삭제와 카운터 정합성 검증 (2026-09-23)

## 문제와 범위

Claude 사후 검수에서 댓글 생성은 게시글 행을 먼저 잠그지만 삭제는 일반 조회 후 카운터를 감소시킨다는 비대칭을 발견했다. 새 격리 MySQL의 **실제 CommentService 호출**로 재현했다. 기존 Popping 앱이나 운영 DB에 요청하지 않았다.

수정 전 신규 7개 테스트 중 5개가 실패했다. 이는 무작위 부하의 실패 확률이 아니라, DB 잠금으로 충돌 구간을 만든 기능 재현이다.

| 시나리오 | 기대 | 수정 전 관측 |
|---|---|---|
| 회원·게스트 댓글을 동시에 삭제 | 행 0 / 카운터 0 | 행 0 / 카운터 1 |
| 생성과 삭제 경합 | 행 1 / 카운터 1 | 행 1 / 카운터 0 |
| 동일 댓글 중복 삭제 | 1회 성공, 다음 요청은 COMMENT_NOT_FOUND | 두 번째 요청에서 ObjectOptimisticLockingFailureException |
| 부모·자식·손자 삭제, 무관한 댓글 1개 유지 | 행 1 / 카운터 1 | 행 1 / 카운터 3 |
| 답글 생성과 부모 삭제 경합 | 정해진 커밋 순서에 맞는 삭제 완료 | 삭제에서 외래키 제약 위반 |

원본: `_workspace/comment-count/2026-09-23/delete-v1/baseline/`. 기존 서비스·테스트 소스, Gradle 로그, XML, HTML, 해시, 실패 내역을 보존했다. baseline의 대기자 투입 순서는 DB의 FIFO 보장을 뜻하지 않는다. 해당 실행에서 관측한 오류와 카운터가 재현 근거다.

## 비교와 선택

| 선택지 | 해결 범위 / 비용 | 결정 |
|---|---|---|
| 카운터를 SQL로 원자 감소 | 오래된 절대값 덮어쓰기는 피하지만, 실제 삭제 개수·중복 삭제·답글 생성과 cascade 삭제 순서는 별도로 해결해야 한다 | 이번 해결책으로 단독 채택하지 않음 |
| postId를 댓글에서 먼저 찾고 READ_COMMITTED로 변경 | 잠금 후 다음 읽기가 최신 데이터를 보도록 만들 수 있으나, 기존 트랜잭션에 합류할 때 격리 수준 적용 문제가 남는다 | 불필요한 선조회·격리 수준 변경을 피함 |
| URL의 postId로 게시글 잠금부터 획득 | 기존 생성과 같은 잠금 순서를 사용하고, 잠금 대기 이전의 댓글 스냅샷 생성을 피한다 | 채택 |
| 변경하지 않고 TTL만 축소 | DB에 저장된 잘못된 카운터는 캐시 만료 후에도 남는다 | 제외 |

두 삭제 endpoint는 원래 postId를 받고 있었지만 서비스에 전달하지 않았다. 이제 `postId, commentId`를 모두 전달한다. 서비스는 게시글 잠금 → 댓글 조회 및 게시글 일치 확인 → 작성자/비밀번호 확인 → 하위 트리 확인 및 개수 계산 → 카운터 감소 → 기존 cascade 삭제를 수행한다. 커밋 후 캐시 무효화는 유지한다.

생성에서도 다른 게시글의 부모 댓글을 지정할 수 없게 했다. 한 게시글의 잠금으로 트리를 보호하려면 같은 트리의 댓글이 같은 게시글에 속해야 하기 때문이다. 이미 잘못 연결된 하위 댓글이 발견되면 다른 게시글의 데이터를 함께 지우지 않고 실패한다. 카운터가 삭제 개수보다 작으면 0으로 덮어 숨기지 않고 롤백한다.

MySQL REPEATABLE READ의 일반 조회 스냅샷은 첫 consistent read에서 생긴다. 잠금 조회와 일반 스냅샷 조회는 구분해야 한다. 이번 선택은 첫 게시글 잠금 뒤 댓글의 일반 조회가 시작되는 현재 호출 경로에 근거한다. [MySQL consistent read 문서](https://dev.mysql.com/doc/refman/8.0/en/innodb-consistent-read.html), [locking read 문서](https://dev.mysql.com/doc/refman/8.0/en/innodb-locking-reads.html).

## 검증 방법과 결과

- 실제 MySQL `performance_schema.data_lock_waits`에서 요청이 대상 게시글 잠금을 기다리는지 확인한다. 시간 지연만으로 충돌을 가정하지 않는다.
- 두 삭제의 충돌은 외부 트랜잭션이 게시글을 잠근 상태에서 두 실제 서비스 요청의 대기를 확인한다.
- 선후가 중요한 세 경우는 최종 테스트에서 첫 서비스 쓰기를 커밋 전 상태로 유지한다. 두 번째 서비스가 DB에서 기다리는 것을 확인한 뒤 첫 트랜잭션을 커밋한다. DB 대기열의 FIFO 순서를 가정하지 않는다.
- 저장 카운터와 `COUNT(*)`를 별개로 검증한다. 회원/게스트, 하위 트리, 생성→삭제, 삭제→생성, 중복 삭제, 권한 실패, 다른 게시글 경계, 과거 잘못된 연결, 카운터 부족, 롤백을 포함한다.
- MVC 테스트 2개로 URL postId가 실제 삭제 서비스에 전달되는 것을 확인한다.

최초 수정 후 대상 테스트는 28개 모두 통과했다. 경계 테스트를 추가한 전체 회귀도 204개 모두 통과했다. 이어 선후 제어를 강화한 최종 전체 실행도 **204 tests / failures 0 / errors 0 / skipped 0**을 확인했다. `final-suite/result.json`과 `verification.json`을 최종 근거로 삼는다. 최종 삭제 MySQL 테스트는 14개이며 이 204개에 포함된다.

실험 runner는 별도 loopback MySQL/Redis 2개를 생성한다. 고유 label과 정확한 container ID를 확인한 대상만 제거하고, 시작 시 존재한 10개 컨테이너 ID 보존 여부를 기록한다. 모든 테스트는 `--rerun-tasks`로 실행했다. 저장 XML의 test/failure/error/skipped를 집계하며, 선택 소스는 실행 전후 해시가 같은지 대조한다. 저장소 전체의 원자적 출처 증명은 아니다.

## 검수·단순화

독립 Codex 검토에서 URL postId를 활용하는 대안과 필요한 경계 테스트를 확인했다. 큐 투입 순서가 FIFO를 보장하지 않는다는 지적을 받아 최종 테스트를 강화했다. Claude 사용 한도로 이번 수정의 Claude 재검수는 아직 받지 못했다.

새 저장소 메서드, 격리 수준 변경, 새 캐시·분산 시스템은 추가하지 않았다. 회원/게스트 삭제는 트리 개수 계산을 공유하고, 기존 cascade 의미를 유지한다.

## 한계

- 현재 controller에서 시작하는 서비스 트랜잭션을 검증했다. 이미 오래된 RR 스냅샷이나 Post/children 관리 객체가 만들어진 외부 트랜잭션에 합류하는 임의 호출은 같은 보장 대상이 아니다. 현재 설정은 open-in-view=false다.
- 기존 DB의 잘못된 카운터·게시글 간 연결을 자동 정리하지 않았다. 카운터가 부족하거나 잘못 연결된 트리는 삭제를 거절한다. 과거 데이터 점검·복구는 별도 작업이다.
- 큰 댓글 트리를 읽고 cascade 삭제하는 비용, 같은 인기 게시글의 쓰기 직렬화 비용은 측정하지 않았다. 기존 cascade의 깊이 제한도 개선하지 않았다.
- 게시글 수정 등 다른 Post 쓰기 경로까지 모든 동시성 문제를 해결했다고 주장하지 않는다.
- 서비스 직접 호출과 MVC 전달 테스트다. 원격 배포, 운영 트래픽, 실제 HTTP 부하, 처리량 개선률을 검증한 결과가 아니다.

다음 작업 후보는 캐시 loader 예외 때문에 sticky 유무에 따라 404/500이 달라지는지 확인하는 것이다. 이번 변경에는 포함하지 않았다.

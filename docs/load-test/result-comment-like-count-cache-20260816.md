# 댓글 좋아요 카운트 마이크로 캐시 — 부하테스트 결과 (2026-08-16)

**판정: 효과 없음. 변경은 폐기했다.**

사전 선언한 지표(마지막 120초 TPS, 임계치 3%)에서 차이는 **−0.1%**였다. 통계 이전에 애초에 움직이지
않았다. 다만 이 실험은 코드를 남기지 못한 대신 **replica가 실제로 무슨 일에 시간을 쓰는지에 대한 실측**을
남겼고, 그로부터 더 큰 대안이 나왔다. 아래 「무엇이 남았나」 참조.

측정 절차는 [`measurement-protocol.md`](./measurement-protocol.md)를 따랐다.

## 1. 무엇을 측정했나

`CommentService.getCommentPage()`는 항상 page 0을 요청하므로 `enrichComments(base, page == 0, ...)`의
`refreshLikeCounts`가 언제나 참이다. 따라서 `commentFirstPage` 캐시에 **히트해도**
`commentRepository.findLikeCountsByIds(ids)`(IN 절 30~100개)가 매 요청 실행된다. 캐시된 읽기 경로에
replica 쿼리가 하나 남아 있는 셈이다.

**변경**: 신규 Caffeine 캐시 `commentLikeCounts` — key `postId`, TTL **3초**, maxSize 500,
`cache.get(key, Callable)` 경유(스탬피드 방지). 좋아요 변경 시 evict하지 않고 TTL만으로 신선도를 잡는다.

**가설**: 이 쿼리를 캐시된 경로에서 걷어내면 replica 부하가 내려가고 처리량이 오른다.

## 4. 왜 효과가 없었나

캐시는 고장나지 않았다. 모든 요청에서 조회됐다(91,008 = `commentFirstPage`와 동일). **문제는 3초 TTL이
이 트래픽 분포에 비해 짧다는 것이다.**

게시글이 2,200개(Hot 200 + Normal 2,000)이고 앱이 2대이므로, 인스턴스 하나가 보는 **게시글당 요청 간격**은

- Hot: 82 TPS ÷ 2 인스턴스 ÷ 200 게시글 = 0.205 req/s → 평균 간격 **약 4.9초**
- Normal: 82 TPS ÷ 2 ÷ 2,000 = 0.021 req/s → 평균 간격 **약 49초**

둘 다 TTL 3초보다 길다. 즉 **대부분의 항목이 다음 요청이 오기 전에 만료된다.** 포아송 근사로 Hot의
재사용률은 `1 − e^(−3/4.9) ≈ 46%`, Hot이 트래픽의 절반이므로 전체 기대 히트율은 20% 남짓 —
실측 15.9%와 같은 자릿수다.

결과적으로 제거된 쿼리는 전체의 15.9%뿐이었다.

### 그런데 그 쿼리는 비쌌는가 — performance_schema 실측

"히트율이 낮아서 효과가 없었다"와 "그 쿼리가 애초에 안 비쌌다"는 서로 배타적이지 않다. 구분하려고
replica의 statement digest를 읽었다(세션 전체 = 6 arm × 3패스 누적).

| 쿼리 | 실행 | 시간 비중 | 검사 행 | **검사 행 비중** |
|---|---|---|---|---|
| **`findLikeCountsByIds`** | 1,385,331 | 11.9% | 88.7M | **47.3%** |
| 재귀 CTE (댓글 트리) | 687,212 | 18.8% | 57.2M | 30.5% |
| 게시글 목록 | 761,598 | 2.1% | 15.2M | 8.1% |
| 닉네임 조회 | 687,191 | 3.5% | 13.1M | 7.0% |

**검사 행 기준으로 replica 작업량의 47.3%가 이 쿼리 하나다.** 재귀 CTE보다 크다. 즉 겨냥한 곳은 맞았고,
"안 비쌌다" 쪽 가설은 기각된다.

> **시간 비중이 아니라 검사 행을 봐야 한다.** replica가 CPU 포화 상태라 `avg` 시간에는 큐 대기가 섞인다.
> 실제로 개인화 반응 조회는 검사 행이 0인데 평균 40ms로 찍힌다. 순수 작업량 지표는 검사 행이다.

**따라서 산술이 맞아떨어진다**: 겨냥한 부하가 47.3%, 캐시가 걷어낸 비율이 15.9% →
실제 절감은 replica 작업량의 약 7.5%. 앱 전체 처리량 기준으로는 그보다 작다.
이 부하 모델의 **검출 한계가 약 4%**이므로 검출되지 않은 것이 당연하다.

## 5. 프로토콜에서 드러난 문제 2가지

**(1) `run-ab.sh`의 워밍업 전 복제 대기 예산이 부족하다 — 실제로 실행이 중단됐다.**

arm 2가 `replication lag never reached 0 (last=701)`로 죽었다. 확인해보니 복제는 정상이었고
(IO/SQL Running, 에러 없음, 워커 2개 ON) 중단 직후 **마스터·replica GTID가 3550308로 완전히 일치**했다.
단지 예산 안에 못 들어왔을 뿐이다.

원인은 워밍업 **전** 대기가 `LAG_WAIT_TRIES=100`(500초)인데, 워밍업 **후** 대기는 1800초라는 비대칭이다.
세션 첫 arm은 지연 0에서 출발하므로 걸리지 않지만, **2번째 이후 arm은 직전 arm의 본 측정이 남긴
백로그(이번엔 1.85만 트랜잭션)에서 출발한다.** 지금까지 안 걸렸던 것은 arm 사이에 사람이 개입해
간격이 벌어졌기 때문으로 보인다. 이번 실행은 `LAG_WAIT_TRIES=360`으로 올려 재개했다.

부수적으로, `Seconds_Behind_Source`가 619 → 701로 오르다 0으로 떨어지는 것을 관찰했다. 다중 스레드
복제에서 이 값이 단조 감소하지 않는다는 규칙 5의 근거가 하나 더 늘었다.

**(2) arm 5만 워밍업 패스가 1회였다 — 통제 이탈.**

JIT 증가율이 1패스에서 0.0110으로 이미 기준(0.02) 아래였다. 다른 5개 arm은 1패스 0.182~0.192였다.
컨테이너는 정상 재생성됐고(로그 확인), JIT 카운터도 18.6k에서 489k로 정상 상승 후 평탄해졌다 —
스테일 시계열 아티팩트가 아니라 실제로 한 패스 만에 컴파일이 끝났다.

원인은 미규명이다. arm 5는 STEADY 판정을 통과했고 TPS 622.6으로 before arm의 중간값이라 결과를
왜곡한 흔적은 없지만, **워밍업 게이트 하나만 믿으면 안 된다는 사례**다. 두 번째 게이트(STEADY 판정)가
있는 구조가 값을 했다.

## 6. 무엇이 남았나 — 다음 작업

실측 프로파일에서 더 큰 대안이 나왔다.

**재귀 CTE는 이미 `like_count`와 `dislike_count`를 읽어온다**(`CommentRepository.java:68-69`), 그리고
`CommentResponse.mapToResponse`가 그 값을 그대로 쓴다(`CommentResponse.java:48-49`). 즉
**`commentFirstPage`가 미스일 때는 방금 DB에서 신선한 카운트를 읽은 직후인데, 곧바로 같은 컬럼을
`findLikeCountsByIds`로 다시 읽고 있다.** 재조회가 필요한 것은 캐시 **히트**일 때뿐이다(그때만 최대
10분 된 값이므로).

`commentFirstPage` 미스가 45.5%이므로:

| | 절감 (replica 작업량) | 신선도 손실 |
|---|---|---|
| TTL 3초 캐시 (폐기됨) | 47.3% × 15.9% ≈ **7.5%** | 최대 3초 + 복제 지연 |
| **미스 경로 재조회 생략** | 47.3% × 45.5% ≈ **21.5%** | **0** (같은 트랜잭션에서 읽은 값) |

3배 크고 트레이드오프가 없다. 데이터셋 크기나 트래픽 분포에도 의존하지 않는다.

TTL을 늘리는 방향(30초 등)은 이 대안을 적용해 남는 비용을 다시 잰 뒤에 판단한다.

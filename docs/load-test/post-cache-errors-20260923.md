# 게시글 캐시 예외 경계 검증 — 2026-09-23

## 결과

게시글 상세 캐시의 로더에서 발생한 `POST_NOT_FOUND`가 `Cache.ValueRetrievalException`으로 감싸져 MVC 오류 화면에서 `INTERNAL_ERROR`로 분류되는 문제를 재현하고 수정했다. 캐시 경계에서 **직접 원인이 `CustomAppException`인 경우만 동일 예외를 재전파**한다.

게시판 첫 페이지도 함께 검증했지만 같은 수정은 적용하지 않았다. `getBoard(slug)`는 캐시 로더 밖에서 실행되며, 현재 로더는 목록 저장소 조회와 DTO 생성만 수행한다. 없는 게시판 오류는 캐시 유무·두 번째 페이지 모두 정상 분류됐다.

**이번 결과는 HTTP 404 복구가 아니다.** 실제 `PostController`·`BoardController`는 HTML MVC 컨트롤러이고, 기존 `MvcExceptionHandler`는 상태 코드를 지정하지 않는다. 테스트에서 오류 모델과 함께 HTTP 200이 관측됐다. 이번 수정은 모델의 오류 분류를 복구했으며, MVC HTTP 상태 정책 개선은 별도 미완료 항목이다.

## 선택한 방법

| 대안 | 판단 |
|---|---|
| 상세 캐시 경계에서 직접 도메인 예외만 복원 | 채택. 확인된 도메인 의미를 보존하고 예상하지 못한 로더 실패는 기존 서버 오류 분류 유지 |
| 전역 MVC advice에서 예외 원인을 재귀 탐색 | 제외. 관련 없는 래퍼 내부 원인까지 도메인 오류로 분류할 수 있고 영향 범위가 넓음 |
| 두 캐시 경로 모두 예방적으로 수정 | 제외. 목록 로더에는 현재 자연스럽게 도메인 예외를 던지는 코드가 없음 |
| 캐시 제거 | 제외. 오류 경계 수정으로 해결 가능하며 정상 캐시 적중을 유지할 수 있음 |
| 댓글·게시글용 공통 캐시 유틸리티 도입 | 보류. 짧은 두 경계를 통합하려고 새 추상화를 만들 필요가 없음 |

운영 코드 변경은 `PostService#getPostDetailFromCache`의 한 경계다. 캐시 TTL, 목록 조회, 전역 예외 처리기, 조회수 증가 순서는 바꾸지 않았다.

## 검증과 원자료

원자료: [`_workspace/cache-errors/2026-09-23/post-mapping-v1`](../../_workspace/cache-errors/2026-09-23/post-mapping-v1/).

| 실행 | 테스트 | 실패 | 오류 | 건너뜀 |

| baseline-v2 / 수정 전 새 테스트 | 15 | 3 | 0 | 0 |

| final-suite / 전체 회귀 | 231 | 0 | 0 | 0 |

수정 전 실패는 캐시 상세의 `POST_NOT_FOUND → INTERNAL_ERROR`, 직접 도메인 예외 인스턴스 유실, 실패 후 재시도 시나리오의 첫 오류 분류였다. `baseline`은 Docker 접근 제한으로 생성 전 중단된 사전 실행이며 테스트 수에 포함하지 않는다.

새 `PostCacheErrorMappingTest` 15개는 다음을 확인한다.

- 상세 캐시 사용/캐시 객체 부재 시 같은 도메인 오류 코드·메시지.
- 상세·목록 저장소 실패는 `INTERNAL_ERROR`와 공용 메시지 유지, 내부 상세 미노출.
- 목록 캐시 사용/객체 부재/두 번째 페이지에서 없는 게시판 오류 유지, 목록 저장소 미호출.
- 캐시 안의 임의 `IllegalArgumentException`과 다른 래퍼 안의 도메인 예외를 잘못 재분류하지 않음.
- 실패 결과는 캐시에 남지 않고, 다음 성공 후 세 번째 요청은 저장소 재조회 없이 캐시 적중.
- 상세의 직접 도메인 예외 인스턴스 보존.

실제 Caffeine·서비스·MVC 컨트롤러·advice를 사용했다. 저장소와 `TransactionTemplate` 콜백은 mock이다. `CACHE_ABSENT`는 빈 `SimpleCacheManager`로 해당 분기를 검증한 것이며 실제 `nocache` 프로파일 부팅 검증이 아니다. 템플릿 렌더링·전체 Security 체인·트랜잭션 프록시는 이 15개의 검증 범위가 아니다.

각 실행은 전체 테스트 실행 도구와 같은 격리 MySQL·Redis를 사용하고 생성한 두 컨테이너만 제거했다. 기존 실행 중 컨테이너 10개의 ID가 유지됐음을 확인했다. Docker 의존성을 띄웠다는 사실이 새 MVC 테스트의 실제 JDBC 검증을 뜻하지는 않는다.

각 실행의 `result.json`, `tests/` XML, `report/` HTML, `source/` 선택 소스 스냅샷을 보존했다. `verify.py`가 XML 수·정리 결과·스냅샷 SHA를 재대조했고, 최종 실행의 선택 소스와 현재 파일이 일치한다. 저장소 전체의 원자적 실행 귀속 증명은 아니다.

## 검토 및 남은 범위

독립 Codex 설계·최종 코드 검토에서 추가 수정이 필요한 결함은 발견되지 않았다. simplify 검토는 짧은 지역 catch 유지로 마쳤다. 실제 Claude 검수 완료 여부는 별도 검수 기록을 따른다.

- MVC 오류의 HTTP 200 응답은 별도 개선 대상으로 남는다. 다음 작업에서는 오류 모델뿐 아니라 HTTP 상태, 기존 오류 화면, redirect/폼 검증과의 경계를 함께 검증해야 한다.
- 조회수 증가가 상세 조회 성공 전 실행되는 기존 순서는 이번 수정의 보장 범위가 아니다.
- 저장소의 임의 입력 오류 등 모든 예외를 캐시 유무와 무관하게 통일했다는 주장은 하지 않는다.
- 배포·커밋·푸시는 하지 않았다. 기존 댓글 캐시 오류 글과 같은 원인이므로 별도 블로그를 늘리지 않고 이 후속 검증 기록으로 연결한다.

## 1. 목적

앱 2대(HAProxy roundrobin, sticky 없음) 환경에서 각 JVM 메모리에 남아 있는 상태 때문에
다른 인스턴스 사용자가 오래된 화면을 보거나 실시간 갱신을 받지 못하는 문제를 줄인다.
이미 정리한 것: 세션(Redis, PR #138), 게시글 상세 캐시(기본 OFF, 2026-09-24).
이번 범위: 캐시 무효화 전파, WebSocket 좋아요 중계, 그리고 장애 시 보장 범위의 실측.

## 2. 이 변경이 고치는 것과 고치지 못하는 것

| 대상 | 현재 | P1′ 이후 |
| --- | --- | --- |
| 게시판 첫 페이지 캐시 (TTL 5분) | 쓰기를 처리하지 않은 인스턴스는 최대 TTL 동안 이전 목록 | 무효화 전파로 반대편도 즉시 evict |
| 댓글 첫 페이지 캐시 (TTL 5초) | 반대편 잔존 최대 5초 | 무효화 전파 (효과 작음) |
| WebSocket 좋아요 | 처리한 인스턴스의 구독자에게만 전달 | 양쪽 구독자에게 전달 + 주기 재동기화 |
| **Replica 지연 중 캐시 재적재** | evict 뒤 지연된 Replica에서 다시 채워질 수 있음 | **고치지 않음.** 재현·기록만 (§8) |

캐시 재적재는 Replica를 읽는다 (`CommentService.java:237`, `PostService.java:239`).
따라서 전파가 빨라도 Replica가 따라오지 못했으면 오래된 값이 다시 채워진다.
TTL은 엔트리 체류 시간을 제한할 뿐 커밋 이후의 최신성을 제한하지 않는다.
`scaling-roadmap.md:134`의 "최대 피해 5초" 문장은 이 이유로 틀렸고 U5에서 정정한다.

## 3. 결정 사항

| ID | 결정 | 이유 | 기각한 대안 |
| --- | --- | --- | --- |
| D1 | 설정 두 개로 분리: `app.cache.invalidation=local\|redis`, `app.websocket.relay=local\|redis`. 기본 `local` | 세션·캐시·WebSocket을 각각 켜고 되돌릴 수 있음. Redis 없는 환경(단일 인스턴스, 테스트) 유지 | `app.session.store`에 묶기(독립 롤백 불가), 항상 켜기(Redis 없는 환경 깨짐) |
| D2 | WebSocket: JVM별 SimpleBroker 유지 + Redis Pub/Sub 중계 | 기존 Redis 재사용, 인프라 증가 없음 | RabbitMQ STOMP broker relay (컨테이너·운영 부담 대비 필요한 보장이 at-most-once 수준) |
| D3 | 재동기화: 재연결 시 + 30초 주기로 현재 반응 수 재조회 | 서버 쪽 Redis 구독만 끊기고 브라우저 연결은 살아 있는 경우도 결국 맞춰짐 | 재연결 시에만 (해당 경우를 보장하지 못함) |
| D4 | SockJS fallback 인스턴스 고정 문제는 확인·기록만 | 범위 통제 | HAProxy `/ws` 경로 affinity 수정 (후속 후보) |
| D5 | 메시지 브로커(Kafka/RabbitMQ)는 이 범위에서 쓰지 않음 | 소비자 1종, 리플레이 불필요, 유실은 TTL·재동기화로 보정 가능 | — (Kafka는 FinBound F1에서 별도 근거로 사용) |

## 4. 수용 기준

| # | 기준 |
| --- | --- |
| AC1 | `redis` 모드에서 한 인스턴스의 글·댓글 쓰기 후 반대편 인스턴스의 해당 캐시가 evict된다. 실험 §7에서 전후 stale 시행 비율을 보고한다 |
| AC2 | `redis` 모드에서 한 인스턴스를 거친 좋아요가 반대편 인스턴스 구독자에게 전달된다. 수신율을 전후로 보고한다 |
| AC3 | 재연결 시와 30초마다 현재 반응 수를 다시 받아 화면을 맞춘다 |
| AC4 | Redis 발행이 실패하거나 지연돼도 사용자 쓰기 요청은 성공한다 (타임아웃·예외 격리) |
| AC5 | 롤백된 트랜잭션은 무효화·좋아요 메시지를 발행하지 않는다 |
| AC6 | `local` 모드 동작은 현재와 같다 (좋아요는 로컬 구독자에게 계속 전달) |
| AC7 | 장애 실험 §8 결과를 기록한다. 발견한 문제는 이 범위에서 고치지 않는다 |

### U1. 캐시 무효화 전파 (10/3)

- `CacheEvictListener`: 로컬 evict와 원격 발행을 분리한다. 현재는 로컬 캐시가 없으면(`:20`) 발행까지 건너뛴다.
- 전송 형식: `{cacheName, key(Long), originInstanceId}`. `CacheEvictEvent.key`가 `Object`라 JSON 왕복에서 `Long`이 `Integer`로 바뀌면 원격 evict가 조용히 실패한다.
- 수신: 자기 origin은 무시하고 로컬 evict.
- 발행 실패·지연은 로그·지표로 남기고 요청에는 전파하지 않는다.
- `fallbackExecution=true` 경로(트랜잭션 없는 호출)의 의미를 테스트로 고정한다.
- 테스트: 키 직렬화 왕복 / 롤백 시 미발행(실제 AFTER_COMMIT 연결) / 발행 예외·타임아웃 격리 / 자기 메시지 무시 / 수신 후 evict / `local` 모드에서 Redis 빈 미생성 / Redis 재구독.

### U2. 좋아요 중계 (10/4)

- `LikeService`의 결과를 커밋 후 이벤트로 옮긴다. 현재는 `@SendTo`가 트랜잭션 밖 반환값을 보낸다.
- 커밋 후: 로컬 브로커로 1회 전송 → `redis` 모드면 Redis 발행. 수신 측은 자기 origin 무시 후 로컬 브로커로 전송.
- `@SendTo` 제거. `local` 모드는 로컬 전송만 (AC6).
- 메시지는 절대 수치를 담으므로 중복은 무해하지만, 늦게 도착한 메시지가 최신 값을 덮을 수 있다(순서 미보장, 문서화).
- 테스트: 커밋 전 미발행 / 롤백 미발행 / 중복 전송 없음 / 자기 메시지 무시 / `local` 모드 동작 유지.

### U3. 재동기화 (10/4)

- 현재 반응 수를 조회할 API가 없다(확인함). 게시글·첫 페이지 댓글의 like/dislike 수를 돌려주는 읽기 API를 추가하거나 기존 댓글 GET을 재사용한다 (구현 시 결정, 읽기 전용).

## 7. 전파 효과 실험 설계

- **Replica 효과와 분리**: 두 앱이 같은 Primary만 읽게 해서 전파 효과만 잰다. Replica 지연은 §8에서 따로.
- **경로 고정**: HAProxy를 거치지 않고 앱 포트로 직접 요청. 쓰기 인스턴스와 읽기 인스턴스를 A→B, B→A 번갈아.
- **사전 조건**: 매 시행 전 반대편 캐시를 채우고 hit를 확인.
- **교란 제거**: `postDetail` OFF 유지. 조회수 flush가 캐시를 지우는 경로가 섞이지 않게 하고, pending/in-flight=0을 완료 신호로 쓰지 않는다 (`post-cache-consistency-20260924.md`).
- **규모**: 방향 × 캐시 종류(게시판, 댓글)마다 독립 시행 100회 이상, 여러 블록으로 나눔. 연속 폴링 샘플을 독립 시행으로 세지 않는다.
- **보고**: stale 시행 비율과 회복 시간을 따로. `local` 모드(전) 대 `redis` 모드(후), 같은 JAR.
- **WebSocket**: 양쪽 구독 준비를 확인한 뒤 실제 STOMP로 좋아요. 분모 = 커밋된 이벤트 수 × 기대 수신자 수.

## 8. 장애 실험 (기록만, 시간 제한)

| 실험 | 기록할 것 |
| --- | --- |
| 실행 중 Redis 중지 | 회원·비회원 요청 결과 (비회원 수정 비밀번호 확인도 `HttpSession` 사용, `PostController.java:102`), 무효화·중계 동작 |
| Redis 재시작 | 기존 세션 상태 (영속화 OFF: `--save ""`, `--appendonly no`), 재구독 여부 |
| Redis 없이 `redis` 모드로 기동 | 기동 실패/지연 여부 (degraded 기동 정책 필요성 판단) |
| Replica 중지 | 읽기 결과 (Primary 장애 전환 없음, `StickyAwareRoutingDataSource.java:33`) |
| Replica 지연 중 evict | 지연된 Replica에서 캐시가 다시 채워지는 현상 재현 |
| SockJS fallback | WebSocket 차단 시 xhr 전송이 roundrobin에서 동작하는지 |

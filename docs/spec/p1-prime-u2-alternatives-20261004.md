## 1. 지금 동작 (코드 확인)

```
사용자 X ─(WebSocket: app-1)─ 좋아요 ─▶ app-1: DB 반영 → @SendTo /topic/like-updates
                                                → app-1에 연결된 사람에게만 전달
사용자 Y ─(WebSocket: app-2)─ 아무것도 못 받음 → 새로고침해야 반영
```

| 사실 | 의미 |
|---|---|
| 서버마다 따로 있는 SimpleBroker | 반대편 서버 시청자는 못 받음. roundrobin이라 약 절반(구조상 추정, 미측정) |
| 메시지는 **절대값**(현재 좋아요 수) | 중복은 무해. 하나 놓쳐도 다음 메시지가 맞춰 줌. 단 늦게 온 옛 숫자가 새 숫자를 덮을 수 있음 |
| 누른 사람 본인 화면도 브로드캐스트로 갱신 | 본인은 요청한 서버에 붙어 있어 정상 |
| **이미 커밋 후에 보냄** (Codex 확인) | 서비스 트랜잭션 프록시가 반환된 뒤 `@SendTo`가 나감. "커밋 후 이벤트로 옮긴다"는 SPEC U2 항목은 지금 구조에선 불필요 |
| 토픽이 전역 하나 | 모든 글의 좋아요가 모든 접속자에게 감 (낭비, 정합성과는 별개) |
| 재연결 시 숫자 재조회 없음 | 끊긴 동안 놓친 변화는 새로고침 전까지 남음 |
| 캐시와 다른 점 | **TTL이 없다** → 놓친 갱신이 저절로 맞춰지지 않음 |

## 2. 대안 비교

| 대안 | 전달 | 어긋남 상한 | 주요 실패 | 코드 규모(Codex 추정) |
|---|---|---|---|---|
| **그대로** | 반대편 없음 | 새로고침까지 | — | 0 |
| **본인 화면만 갱신** (브로드캐스트 제거, HTTP 응답으로 갱신) | 타인 실시간 없음(의도) | 새로고침까지 | — | 40~100줄, WS 코드 삭제 가능 |
| **Redis Pub/Sub 중계** | 최대 1회, 유실 가능 | 유실 시 다음 메시지/새로고침까지 | Redis 장애·큐 가득·구독 끊김 → 조용히 유실 | 200~350줄 (U1 코드 재사용) |
| **주기 재조회(폴링)** | 결국 맞춰짐 | 폴링 간격 + Replica 지연 | 폴링 실패 중엔 멈춤 | 100~220줄, 조회 부하 상시 |
| **Pub/Sub + 재조회** | 실시간 + 보정 | 보정 주기 | 늦은 푸시가 새 조회값을 덮을 수 있음 → 버전 필요 | 350~600줄 |
| 외부 STOMP 브로커(RabbitMQ) | 기본은 최선 노력 | 브로커 장애 시 본인 화면도 멈춤 | 인프라 추가 | 50~150줄 + 운영 |
| 게시글별 같은 서버로 연결 고정 | 같은 서버면 로컬 전달 | 재시작·재해시 때 갈라짐 | HAProxy는 연결 단위로만 라우팅, SockJS 다중 요청 처리 필요 | 100~250줄 + 설정 |
| Redis Streams | ACK 설계 시 최소 1회 | 보존 기간 | 서버별 소비 그룹 필요, 브라우저 재생은 따로 | 450~900줄 |
| SSE + Pub/Sub | Pub/Sub와 같음 | 같음 | Last-Event-ID로 없던 기록이 생기진 않음 | 250~450줄 |
| Kafka | 저장 후 최소 1회 | 지연·보존 | 커밋~발행 사이 구멍, 운영 비용 최대 | 400~800줄 |

게시글별 토픽 분리: 전달 보장과 별개인 최적화. 낭비가 측정상 의미 있을 때 검토(댓글 좋아요는 부모 글 id를 서버에서 확인해야 라우팅 가능).

## 3. 추천이 갈린다

| | Codex | Claude |
|---|---|---|
| 추천 | **본인 화면만 갱신**, 실시간 필요가 확인되면 Pub/Sub 재검토 | **Redis Pub/Sub 중계 + 재연결 시 한 번 재조회** |
| 핵심 근거 | 실사용자가 없어 잃을 게 없음. 구독·재연결·중계 운영 면적을 통째로 없앰. "이미 만든 코드가 있다"는 채택 이유가 아님 | 운영(=로컬 2대) 기준으로 **이미 있는 기능이 절반만 동작**. TTL이 없어 저절로 안 맞춰짐. 메시지가 절대값이라 유실 보정이 쉬움 |
| 약점 | 기능 축소. "타인 실시간 좋아요"를 버리는 제품 판단 | 유실·순서 미보장. U1 테스트는 Redis 프로세스 재시작·메시지 재생까지 검증한 건 아님 |

**Claude 의견:** 사용자가 정한 전제(로컬 2대 = 운영)에서는 "실사용자가 없다"가 기능을 없앨 근거가 되기 어렵다고 본다. 다만 Codex 지적대로 "만들어 둔 코드가 있다"는 이유로 고르면 안 되고, 실시간 좋아요를 **제품이 약속하는 기능으로 유지할지**가 먼저다. 이건 사용자가 정할 제품 판단이다.

## 6. 결정 (2026-10-04) 및 기준값 측정 계획

사용자 결정: **실시간 좋아요 유지 → Redis Pub/Sub 중계 방향. 측정 먼저.**

### 구성
- 이미지: main(`fcd435f`)을 로컬 빌드. 이전 실험 override 재사용(앱 2대, 앱 포트 19091/19092 직접, 풀 10/10, 읽기 Primary). HAProxy 미사용.
- 클라이언트: Node 24 내장 WebSocket으로 SockJS 원시 엔드포인트(`/ws/websocket`)에 접속해 STOMP 프레임 직접 송수신(추가 설치 없음).
- 대상: 실험 전용 게시판 `u2-exp`의 게스트 글 1개. 끝나면 게시판·글·좋아요 행 삭제.

### 측정 1 — 반대편 누락률
- 시청자 4명(서버당 2명)이 `/topic/like-updates` 구독. 행위자 2명(서버당 1명)이 번갈아 좋아요(이벤트마다 새 guestIdentifier → 좋아요 수가 1씩 증가하므로 숫자로 이벤트 식별).
- 서버당 100회, 이벤트 간 0.3초. 2초 안에 못 받으면 누락.
- 산출: (쓴 서버, 받은 서버)별 수신율·지연.

### 측정 2 — 끊김·복구 (다음 쓰기 없이)
- 클라이언트 오프라인 30초(그동안 반대 서버에서 좋아요 5회) → 재연결 → 10초 대기 후 마지막으로 본 숫자 vs DB. 3회.
- 앱 재시작: app-2 재시작 중 app-1에서 좋아요 → app-2 시청자 재연결 후 숫자 vs DB. 3회.

### 이번 범위 밖
- 순서 역전, 메시지량·낭비, Redis 구독 끊김: 중계 구현 후 전후 비교에서 측정.

예상 시간: 30~40분. 성능 측정이 아니라 전달 여부 측정이라 부하테스트 프로토콜 대상이 아니다.

## 7. 기준값 측정 결과 (2026-10-05 새벽, main `fcd435f`)

원자료: `.claude/docs/research/u2-baseline-20261005/` (`miss.json`, `offline.json`, `measure.mjs`)

### 측정 1 — 반대편 누락률 (서버당 시청자 2명, 서버당 좋아요 100회)

| 처리 서버 → 시청자 서버 | 수신 | 지연 p50 / 최대 |
|---|---|---|
| app-1 → app-1 | 200/200 | 15 / 41ms |
| app-2 → app-2 | 200/200 | 15 / 176ms |
| app-1 → app-2 | **0/200** | — |
| app-2 → app-1 | **0/200** | — |

### 측정 2 — 끊김 후 (같은 서버, 다음 쓰기 없이 재연결 10초 대기)

| 회차 | 끊기기 전 화면 | 재연결 후 화면 | DB |
|---|---|---|---|
| 1 | 250 | 250 | 255 |
| 2 | 256 | 256 | 261 |
| 3 | 262 | 262 | 267 |

- 끊긴 30초 동안의 좋아요 5건이 재연결 후에도 반영되지 않는다 → **중계와 별개로 재연결 시 재조회가 필요하다.**
- 첫 시도에서 시청자와 처리 서버를 다른 서버에 두는 바람에 원래 아무것도 받지 못해 의미 없는 값(null)이 나왔다(`offline-crossinstance.json`, `restart-crossinstance.json`). 같은 서버로 다시 쟀다.
- 앱 재시작은 시청자 입장에서 "끊겼다 다시 붙음"과 같아 따로 재지 않았다. 다중 인스턴스 재시작 시나리오는 구현 후 전후 비교에서 잰다.
- 실험 데이터(게시판·글·좋아요 267행)는 삭제했다.

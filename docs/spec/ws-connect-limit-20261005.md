# WebSocket 연결 제한 — 새 게스트 신원 속도 묶기 (2026-10-05)

상태: **구현·검증 완료 (2026-10-05)** — 결과 §7
Codex 검토: `.claude/docs/research/ws-connect-limit-design-codex-20261005.md`
배경: `rate-limit-haproxy-20261005.md` 비목표 1번. 좋아요의 게스트 신원은 WebSocket 핸드셰이크 때 정해진다(PR #170). 쿠키를 지우고 다시 연결하면 새 신원 → 같은 글에 좋아요를 또 누를 수 있다. 연결 수를 묶으면 새 신원이 붙는 속도가 묶인다.

---

## 1. 먼저 확인한 것 — 대체 전송은 이미 깨져 있다 (2026-10-05 실측)

화면은 `transports: ['websocket', 'xhr-streaming', 'xhr-polling']`로 연결한다. 실제 글 화면(헤드리스 Chrome)에서 전송을 하나씩 강제해 STOMP 연결 + 좋아요 추가·취소를 시험했다.

| 경로 | websocket | xhr-streaming | xhr-polling |
|---|---|---|---|
| HAProxy(앱 2대, 라운드로빈) | **4/4 성공** | **0/4** "Lost connection" | **0/5** "Lost connection" |
| 앱 1대 직접(대조군) | 2/2 | 2/2 | 3/3 |

원인(HAProxy 로그): 세션을 연 요청 `POST /ws/965/<세션>/xhr`은 app1(200), 이어진 `POST .../xhr_send`는 app2로 가서 **404** — SockJS 세션이 앱 메모리에 있고 라운드로빈이 다음 요청을 다른 앱에 보낸다.

즉 **지금 운영(앱 2대)에서 동작하는 전송은 websocket 하나뿐**이다. WebSocket을 못 쓰는 환경(일부 회사 프록시 등)의 사용자는 이미 실시간 좋아요를 못 받고, 30초 재조회로만 맞춰진다(U2 설계).

원자료: `.claude/docs/research/ws-transports-20261005/`

## 2. 무엇을 막나

| 위협 | 지금 | 이번 |
|---|---|---|
| 쿠키를 지우고 재연결 → 새 게스트 신원으로 좋아요 반복 | 연결 수만큼 가능 | IP당 WebSocket 연결 수를 분당 N회로 → 새 신원 속도 상한 |
| 연결 폭주(서버 세션·메모리) | 제한 없음 | 같은 제한 |

**막지 않는 것:** 이미 붙은 신원은 연결을 유지하는 한 계속 쓸 수 있다(연결당 신원 1개, 좋아요는 글마다 1번). 한 연결 안의 메시지 폭주(같은 신원이라 수는 안 늘고 DB 부하만) — 필요 시 STOMP 인터셉터로 별도.

## 3. 방안 비교

| 방안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 웹소켓 전용 + 업그레이드 요청만 세기 (채택)** | 화면·서버 모두 SockJS 전송을 websocket만 허용. HAProxy가 `/ws/` 아래의 `Upgrade: websocket` 요청을 IP별로 셈 | 연결 시도 1개 = 셀 요청 1개(거절된 시도도 셈). 앱 2대·라운드로빈인 지금은 이미 깨진 경로만 없앰(앱 1대 배포나 세션 고정 구성이면 대체 전송 사용자가 실시간을 잃음) | WebSocket을 못 쓰는 환경 복구는 포기(지금도 안 됨) |
| B. 대체 전송 고치기 + 세션 시작만 세기 | `/ws/`를 세션 id로 같은 앱에 보내도록 HAProxy 해시 + 세션 생성 요청만 셈 | WebSocket 못 쓰는 환경도 실시간 | 해시 설정·폴링 요청 구분이 복잡. 앱 1대가 죽으면 그 세션은 끊김(지금과 같음) |
| C. 앱(핸드셰이크 인터셉터)에서 세기 | 신원이 실제로 붙는 지점에서 IP별 카운트 | 가장 정확한 지점 | 앱 2대가 따로 세거나(한도 2배) Redis 필요, 앱이 클라이언트 IP를 알려면 X-Forwarded-For를 믿어야 함 |

## 4. 설계 (A안 기준)

### 4-1. 웹소켓 전용

- 서버: `withSockJS().setTransportHandlers(new WebSocketTransportHandler(new DefaultHandshakeHandler()))`. (`setTransportHandlerOverrides`는 기본 전송을 남겨 두므로 웹소켓 전용이 안 됨.) `/ws/info`, SockJS `/ws/{서버}/{세션}/websocket`, 순수 `/ws/websocket`은 그대로, xhr 계열은 404. 화면만 바꾸면 안 된다 — 직접 만든 클라이언트는 xhr로 404를 무릅쓰고 재시도할 수 있다.
- **출처:** `setAllowedOriginPatterns("*")`를 지워 Spring 기본(같은 출처만)으로. HAProxy가 Host를 그대로 넘기므로 설정값 불필요. 게스트 쿠키가 SameSite=Lax라 "다른 사이트가 피해자 신원으로 좋아요"는 원래 성립하지 않지만(쿠키 미전송), 아무 출처나 받는 것은 좁힌다.
- 화면: `transports: ['websocket']`.
- 확인: 핸드셰이크 인터셉터(게스트 신원)가 그대로 적용되는지 테스트.

### 4-2. HAProxy

- 대상: `path,url_dec`가 `^/ws/` 이고 `Upgrade: websocket` 헤더가 있는 요청(SockJS `/ws/{서버}/{세션}/websocket`과 순수 `/ws/websocket` 둘 다).
- 표 `rl_ws`, 기존 묶음과 같은 방식(거절된 시도도 셈, `RATE_LIMIT_OFF`로 끔).
- 한도(제안): **IP당 분당 30회.** 글 화면 1번 = 연결 1번. 빠르게 글을 넘겨 보는 사용자(분당 20개 안팎)와 탭 여러 개를 허용.
- 넘으면 429(업그레이드 실패) → 브라우저 WebSocket은 상태 코드를 알려 주지 않고 `onerror` → close(1006)으로 받는다. 화면은 일반 연결 실패와 구분하지 않고 백오프로 재시도.
- ~~`timeout tunnel 1h` 추가~~ → **넣지 않음**(Codex 리뷰 반영, 실측): 브라우저가 쓰는 SockJS 경로는 서버가 25초마다 하트비트를 보내 60초 client/server 제한에 걸리지 않는다(85초 유지, 하트비트 3회). 하트비트 없는 순수 `/ws/websocket`만 60초에 끊긴다 — 비브라우저 클라이언트가 연결을 오래 붙잡지 못하게 하는 편이 낫다.

### 4-3. 화면 재연결 백오프

지금은 실패하면 5초마다 무한 재시도 → 제한에 걸린 탭이 분당 12번씩 계속 두드려 카운터를 채운다.
- 실패할 때마다 5초 → 10초 → 20초 → 40초 → 최대 60초, ±20% 무작위(동시 재연결 분산). 연결에 성공하면 5초로 초기화.
- **재시도 예약은 한 곳만.** 지금은 `abandonConnection()`의 5초 재시도와 별개로 30초 감시 타이머(`setInterval`)가 끊겨 있으면 바로 `connect()`를 부른다 → 백오프를 무시하고 30초마다 시도(Codex 지적, 코드 확인). 감시 타이머는 "예약된 재시도가 없을 때만" 예약하도록 바꾼다.
- 연결이 끊긴 동안에도 30초 재조회는 계속(U2) → 숫자는 맞춰진다.

### 4-4. 부하테스트

기준 jmx는 STOMP를 쓰지 않는다(좋아요는 HTTP 테스트 API). `RATE_LIMIT_OFF`면 이 묶음도 꺼진다 → 영향 없음.

## 5. 검증 계획

| 확인 | 방법 | 기대 |
|---|---|---|
| 웹소켓 전용 | 실제 화면에서 전송별 시험 | websocket 성공, xhr 전송은 서버가 거절(404) |
| 게스트 신원 | 기존 실측 스크립트(쿠키 고정·본문 위조) 재실행 | 그대로 1개 |
| 한도 | 같은 IP에서 연결 31회 | 31번째부터 429, 그 요청은 앱에 안 감 |
| 정상 화면 | 글 화면 열기·좋아요 | 영향 없음 |
| 백오프 | 한도 초과 상태에서 화면 열어 두기 | 재시도 간격이 늘어남(콘솔·HAProxy 로그) |
| 쿠키 재발급 공격 | 쿠키 없이 연결·좋아요 반복 | 30개 뒤 멈춤 |

**알려진 한계:** 이미 붙은 신원은 연결을 유지하는 한 계속 쓸 수 있다. IP 기준이라 같은 IP 뒤 사용자(로컬에서는 전원)가 한도를 나눠 쓴다. TLS를 앞단에서 끝내게 되면 앱이 forwarded 헤더를 믿도록 설정해야 같은 출처 판정이 맞는다.

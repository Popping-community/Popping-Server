## 1. 무엇을 막나

| 위협 | 이번에 막는 방법 |
|---|---|
| 게스트 글·댓글 도배 | 글·댓글 작성 요청을 IP당 분당 N회로 |
| 로그인·가입·게스트 비밀번호 대입 (BCrypt 비용 소모 포함) | 인증 계열 요청을 IP당 분당 N회로 |
| 이미지 업로드 남용 (S3 비용) | 업로드를 IP당 분당 N회로 |

**이번에 하지 않는 것 (비목표)**
- **WebSocket(좋아요 신원) 제한 — 다음 단위로 분리 (사용자 결정).** 첫 초안의 "`/ws/` 요청 분당 30회 = 새 신원 상한"은 틀렸다: 화면이 허용하는 대체 전송(xhr 폴링)은 메시지마다 HTTP 요청을 보내 정상 탭 하나로도 30회를 넘을 수 있고, 재연결이 5초 간격 무한 반복이라 제한에 걸린 사용자가 계속 두드린다. 또 연결 수 제한은 "새 신원을 붙이는 속도"를 늦출 뿐 이미 붙은 신원은 그대로다. 다음 단위에서: 대체 전송이 앱 2대에서 실제로 동작하는지 확인(라운드로빈이라 깨져 있을 가능성, 미검증) → 웹소켓 전용으로 좁히고 업그레이드 요청만 세기 + 재연결 백오프.
- 한 WebSocket 연결 안의 메시지 폭주, 읽기 요청 남용, 여러 IP 분산 공격.
- 회원 전용 쓰기(게시판 생성·글 수정·삭제)는 로그인이 필요해 이번 대상에서 뺀다.

## 2. 왜 HAProxy인가 (요약)

- 앱·DB에 닿기 전에 거절한다. HAProxy가 1대라 앱 2대가 같은 카운터를 쓴다(peers 불필요).
- Redis에 의존하지 않는다 → Redis 장애 시 보장 범위(일관성 기준 §5)와 무관.

## 3. 설계

### 3-1. 묶음과 한도 (사용자 결정: 제안값으로 시작)

| 묶음 | 대상 | 한도 (IP당 분당) |
|---|---|---|
| 글 작성 | POST `/boards/{slug}/guest`, `/boards/{slug}/member` | 5 |
| 댓글 작성 | POST `/boards/{slug}/{postId}/comments/guest`, `.../member` | 20 |
| 인증 | POST `/login`, `/users/join`, `/boards/{slug}/{postId}/edit-password`, `.../delete-password` · **DELETE** `.../comments/{id}/guest` (게스트 댓글 삭제 = 비밀번호 확인) | 10 |
| 이미지 업로드 | POST `/images/upload` | 20 |

- 묶음마다 표를 따로 둔다(서로 배타적인 조건이라 `track-sc0` 하나로 묶음별 표를 고름). 글을 쓴다고 로그인 한도가 줄지 않는다.
- **거절된 시도도 센다.** 성공 여부와 무관하게 "시도 속도"를 제한한다.
- `http_req_rate(1m)`은 정확한 60초 합이 아니라 **근사 이동 빈도**(이전·현재 구간 가중). 경계에서 한두 건 오차가 있다.
- 표: `type ipv6`(IPv4도 담김), 묶음당 `size 20k`, 10분 미사용 시 만료. **HAProxy 재시작 시 카운터는 0으로 초기화**(수용).
- **한도는 사람이 아니라 IP 합계다.** 같은 IP 뒤의 여러 사용자(회사·학교 NAT)는 함께 센다.

### 3-2. 넘었을 때 (사용자 결정)

- HAProxy가 `429` + `Retry-After: 60` + **간단한 한글 HTML**("요청이 너무 많습니다. 1분 뒤 다시 시도하세요.")을 돌려준다. 앱에 닿지 않는다. 폼 제출(글 작성·로그인 등)에서는 이 페이지가 보인다.
- 댓글 작성은 fetch라 지금은 2xx가 아니면 모두 "댓글 작성에 실패했습니다." 알림(`detail.html` 확인). **429면 "요청이 너무 많습니다. 잠시 뒤 다시 시도하세요." 알림**으로 나눈다. 게스트 댓글 삭제(fetch)도 같은 방식으로 확인 후 반영.

### 3-3. 클라이언트 IP

- HAProxy가 직접 받는 연결의 출발지(`src`). `X-Forwarded-For`는 믿지 않는다.
- **로컬 한계:** 브라우저·JMeter 모두 Docker 게이트웨이 주소 하나로 보인다 → 로컬에서는 "모든 사용자 합계". IP별 분리는 `popping-net` 안의 서로 다른 컨테이너에서 HAProxy로 직접 보내 검증한다(호스트 포트를 거치면 다시 하나로 합쳐질 수 있음).

### 3-4. 부하테스트 스위치

기준 부하테스트는 한 IP에서 로그인 225회(시작 1분 안), 게스트·회원 댓글·글을 보낸다 → 켜진 채면 무너진다.
- `haproxy.cfg`의 제한 부분을 `.if !defined(RATE_LIMIT_OFF)`로 감싼다. 변수는 **존재 여부만** 본다(`=0`도 꺼짐).
- `compose.loadtest.yml`이 haproxy에 `RATE_LIMIT_OFF=1`. **환경 변수는 컨테이너를 새로 만들 때만 반영**되므로 `run-ab.sh`가 앱과 함께 **haproxy도 재생성**한다(지금은 앱만 재생성 — Codex 지적).
- 확인: haproxy 컨테이너 환경에 `RATE_LIMIT_OFF=1`이 있고, 런타임 API(`show table`)에 제한 표가 **없음**. 이를 위해 `global`에 내부용 stats 소켓을 추가한다.
- 부하테스트는 제한 없는 경로를 잰다. 제한 자체의 비용은 미측정.

### 3-5. 관측

HAProxy 로그(429 기록), 런타임 API `show table rl_*`. Prometheus 연동은 범위 밖.

## 5. 검증 계획

| 확인 | 방법 | 기대 |
|---|---|---|
| 한도 | 묶음마다 한도+5회 연속 | 한도까지 앱 응답, 이후 429 + `Retry-After`. 429 요청은 앱 접근 로그에 없음 |
| 묶음 분리 | 글 한도를 채운 뒤 로그인 | 로그인 통과 |
| IP 분리 | `popping-net` 컨테이너 2개에서 각각 | 따로 셈 |
| 회복 | 1분여 대기 | 다시 통과 |
| 정상 사용 | 브라우저로 보기·좋아요·댓글 1건 | 영향 없음 |
| 스위치 | `RATE_LIMIT_OFF=1`로 재생성 → 같은 시험 | 전부 통과, `show table`에 표 없음 |

## 6. 결과 (2026-10-05)

| 확인 | 결과 |
|---|---|
| 한도 | 글 6번째, 댓글 21번째, 로그인 11번째, 업로드 21번째부터 429 + `Retry-After: 60` + 한글 페이지 |
| 앱 도달 | 429 21건 모두 HAProxy 로그에 `http_front/<NOSRV>` (서버로 보내지 않음) |
| 묶음 분리 | 글 한도를 채운 뒤 댓글·로그인·업로드는 각자 한도까지 통과 |
| IP 분리 | `popping-net` 컨테이너 172.19.0.12 / .13: 한쪽이 소진돼도 다른 쪽은 10회 통과. 호스트 요청은 172.19.0.1(게이트웨이) 하나로 보임 |
| 회복 | 약 100초 뒤 로그인 302, 글 200 |
| 인코딩 우회 (Codex 리뷰 Major) | 원래 경로로 매칭하자 `/%6cogin`이 13회 모두 앱의 로그인 처리에 닿음(실측) → `path,url_dec`로 디코딩 후 매칭. 수정 후 인코딩 6 + 일반 6 → 11번째부터 429(같은 예산). `normalize-uri`는 2.8에서 실험 기능이라 쓰지 않음 |
| 화면 | 헤드리스 Chrome으로 실제 글 화면: 정상 댓글 "댓글이 작성되었습니다.", 댓글 한도 초과 · 인증 한도 초과 상태의 게스트 댓글 삭제 → "요청이 너무 많습니다. 잠시 뒤(약 1분) 다시 시도해 주세요." |
| 부하테스트 스위치 | 부하테스트 설정: `RATE_LIMIT_OFF` 있음·제한 표 없음 → 통과, 글 7회 모두 200 / 평소 설정: 확인 절차가 중단 |

**운영 메모:** 부하테스트 뒤 컨테이너는 제한 꺼짐·테스트 API 켜짐 상태로 남는다. 평소 구성으로: `docker compose up -d --force-recreate app-1 app-2 haproxy`.

# 게시판 첫 페이지 캐시 대안 검토 계획 (2026-10-04)

상태: **결정 완료 (2026-10-04)** — 결과 §6~7, 결정은 맨 아래
배경: U1(로컬 캐시 + Pub/Sub 전파, PR #158 보류)의 대안을 검토한다. 사용자 결정: **측정 + Codex 비교**, 기준은 **측정 근거 + 단순함**.

## 1. 먼저 답할 질문

> 게시판 첫 페이지 캐시는 실제로 무엇을 얼마나 아껴 주는가?

이 답에 따라 대안의 무게가 달라진다.
- 아끼는 게 거의 없으면 → **캐시 제거** 또는 **짧은 TTL**이 가장 단순한 답이고, 전파 수단(Pub/Sub·공유 캐시·버전 키) 자체가 불필요해진다.
- 아끼는 게 크면 → 전파 수단 비교(Pub/Sub vs 공유 캐시 vs 버전 키 vs Streams/Outbox)로 넘어간다.

## 2. 코드에서 확인한 사실

- `CacheConfig`: `boardFirstPage`에는 **끄는 설정이 없다** (TTL 5분, 최대 50개).
- `PostService.getPostPage`: **page=0·size=20일 때만** 캐시. page=1은 같은 쿼리(`findPostListByBoard`, offset만 20)를 캐시 없이 실행.
- `getFirstPageFromCache`는 캐시 조회 **전에** `getBoard(slug)`로 DB를 읽는다 → 캐시 적중이어도 게시판 조회 쿼리 1회는 항상 나간다.
- 목록 쿼리에 `ORDER BY` 없음 (별도 백로그).

→ **코드 변경 없이** `GET /boards/board-1`(캐시) vs `GET /boards/board-1?page=1`(캐시 없음)을 비교해 "캐시가 아끼는 비용"을 근사한다.
근사의 한계: offset 20 차이, 화면에 그리는 글 내용 차이(같은 20건 크기). 무시할 수준인지 EXPLAIN으로 함께 확인.

## 6. 결과 (2026-10-04)

원자료: `.claude/docs/research/cache-alternatives-20261004/` (`arms.json`, `explain-analyze*.txt`, `top-digests.txt`, `codex-comparison.md`)

### 측정 (앱 1대, 동시 8, 60초 × 3회씩 번갈아; 중앙값 [최소~최대])

> ⚠️ **프로토콜 미준수 스크리닝.** 확립된 부하테스트 프로토콜(JMeter, 워밍업 패스+JIT 2% 게이트, 600초 중 마지막 120초, STEADY 판정)을 따르지 않았다(Python 8스레드·2분 예열·60초 arm). **처리량·지연·앱 CPU는 JIT 미정상 가능성이 커 결론 근거로 쓰지 않는다.** DB 문장 수·DB 시간·EXPLAIN ANALYZE는 JIT와 거의 무관해 사용한다. (2026-10-04 사용자 지적)

| | 캐시 (page=0) | 캐시 없음 (page=1) |
|---|---|---|
| 처리량 | 465 rps [408~477] | 440 rps [431~447] |
| p50 | 9.66ms [9.64~10.03] | 10.63ms [10.56~10.70] |
| p95 / p99 | 53.2 / 64.7ms | 51.8 / 61.0ms |
| 앱 CPU/요청 | 4.29ms [4.18~4.89] | 4.52ms [4.46~4.58] |
| DB 문장/요청 | 7.97 | 8.97 |
| DB 시간/요청 | 0.93ms | 1.49ms |

- 캐시가 없애는 것은 목록 쿼리 1개(평균 0.55ms, 데워진 EXPLAIN ANALYZE 0.2~0.8ms)뿐.
- 앱 CPU 포화(1.97~1.99코어) — 렌더링(약 47.5KB HTML)이 지배. 처리량·p95·p99·CPU 차이는 범위가 겹치거나 방향이 엇갈림(p95/p99는 캐시 쪽이 나쁨). 3회·같은 호스트·고정 순서·page 0과 1의 차이 → **"효과 없음"도 "효과 입증"도 아님.**
- 캐시 적중에도 매 요청: 게시판 slug 조회 2회(중복) + 읽기 트랜잭션 2개의 `SET autocommit`×4·`COMMIT`×2.

### Codex 비교 결론

| 후보 | 판정 |
|---|---|
| **캐시 제거** | **추천.** 아끼는 비용(0.55ms·쿼리 1개)이 무효화 장치 유지 비용을 정당화하지 못함 |
| 5초 TTL, 전파 없음 | 나중에 캐시가 측정상 필요해지면 가장 먼저 검토 |
| U1 Pub/Sub (PR #158) | 동작은 검증됐지만 지킬 이득이 작음. at-most-once |
| 버전 키 / 공유 Redis 캐시 | 같은 0.55ms를 지키려고 읽기마다 Redis 왕복 추가 |
| Streams·Outbox / CDC / 해시 라우팅 / near cache | 이 규모·이득에 과함 |

- PR #158: Codex는 **닫기** 권고(쓰지 않을 장치를 넣지 않기). 실험·설계 문서는 증거로 가치 있음.
- 별도 수정 후보: 게시판 slug 중복 조회 제거(추정 약 0.49ms·DB 문장 4개 감소, 측정 아님).
- 미측정: 실제 읽기/쓰기 비율, 게시판별 쏠림, 다른 호스트·더 많은 반복, ORDER BY를 넣은 쿼리 비용, 부하 중 다중 인스턴스 동작.

## 7. 댓글 첫 페이지 캐시 측정 (2026-10-04, 사용자 요청 "재보자")

같은 스크리닝 조건(프로토콜 미준수: Python 8스레드·2분 예열·60초 arm × 3회씩 번갈아). **같은 URL**(`GET /boards/board-1/{postId}/comments`)에서 쿠키만 다름: 없음 = 캐시 / `STICKY_PRIMARY=1` = 캐시 건너뜀(이 구성은 읽기도 Primary라 DB 경로 동일). 3회 값이 서로 거의 같아 중앙값만 표기.

| 글 | arm | DB 문장/요청 | **DB 시간/요청** | 앱 CPU/요청 | 처리량 (스크리닝) | p50 (스크리닝) |
|---|---|---|---|---|---|---|
| 댓글 1,342개 (728780) | 캐시 | 3.99 | **0.93ms** | 2.24ms | 887 rps | 7.3ms |
| | 건너뜀 | 5.99 | **52.5ms** | 5.20ms | 84 rps | 98.4ms |
| 댓글 4개 (700106) | 캐시 | 3.98 | **0.45ms** | 1.40ms | 1,233 rps | 5.7ms |
| | 건너뜀 | 5.97 | **1.22ms** | 2.37ms | 737 rps | 7.8ms |

- 캐시가 없애는 것: 재귀 CTE 트리 쿼리(가장 비싼 다이제스트, 평균 5.7ms·많은 글은 수십 ms) + 작성자 조회 등 문장 2개.
- **댓글 많은 글에서 DB 시간 약 56배, 처리량 약 10배 차이.** 처리량 수치는 스크리닝이지만 차이가 프로토콜 검출 한계(약 4%)보다 수백 배 커서 방향은 분명하다. 건너뜀 arm은 DB가 병목(요청당 52ms).
- 보통 글에서도 DB 시간 0.77ms·앱 CPU 약 1ms 절감.
- 원자료: `.claude/docs/research/cache-alternatives-20261004/arms-boards_board-1_*_comments.json`, `top-digests-comments.txt`.

### 결론 (게시판과 반대)

| 캐시 | 아끼는 것 | 서버 간 불일치 | 판단 |
|---|---|---|---|
| 게시판 첫 페이지 | 쿼리 1개, 약 0.55ms | 최대 5분, 글쓴이 본인도 못 봄 | **제거 후보** |
| 댓글 첫 페이지 | 재귀 CTE, 많은 글에서 약 52ms | 최대 5초, 글쓴이는 sticky로 항상 봄 | **유지**, 전파 없이 5초 TTL로 충분 |

→ 두 캐시 모두 Pub/Sub 전파가 필요하지 않은 상태가 된다(PR #158 판단 근거).

## 결정 (2026-10-04)

- **게시판 첫 페이지 캐시: 제거** (`d9edee9`, 브랜치 `refactor/remove-board-first-page-cache`). 아끼는 것이 목록 쿼리 1개(약 0.55ms)뿐이고 다른 앱에서는 글쓴이 본인까지 최대 5분 이전 목록을 봤다. 전파 장치로 지킬 가치가 없다고 판단.
- **댓글 첫 페이지 캐시: 유지, 전파 없음.** 재귀 CTE(많은 글에서 약 52ms)를 막아 준다. 5초 TTL + 글쓴이 sticky 우회로 "본인은 즉시, 다른 사람은 최대 5초". 더 신선해야 하면 Pub/Sub보다 TTL 단축을 먼저 검토(인기 글은 TTL 1초여도 미스가 초당 1회 — 추정, 미측정).
- **U1 Pub/Sub 전파(PR #158): 닫음.** 지킬 캐시가 남지 않는다. 코드는 브랜치 `feat/p1-cluster-local-state`에 보존. 실험·설계 기록은 이 문서들로 남긴다.
- **발견한 더 큰 결함: 게시판 목록에 정렬이 없었다.** board-1(264,427건)의 첫 페이지가 id 8~112, 즉 가장 오래된 글이었다. 실제 게시판에서는 새 글이 첫 페이지에 나오지 않았다. 별도 PR로 `ORDER BY p.id DESC` 수정(기존 인덱스 역방향 읽기, 정렬 단계 없음, 데워진 상태 약 0.16~0.2ms) → 캐시 제거 결론 유지.
- **반성:** 비용을 먼저 재지 않고 전파 장치를 먼저 만들었다. 측정 순서가 거꾸로였다.

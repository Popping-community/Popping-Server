# 앱 읽기를 Primary로 — Replica 읽기 중단 (2026-10-05)

상태: **적용·검증 완료 (2026-10-05)** — 결과 §7
배경: 일관성 기준(`consistency-contract-20261005.md`)의 B등급 공백 1 "글 삭제 후 노출"을 보다가, 노출 시간 = Replica 지연이고 그 지연이 부하 시 수백 초까지 측정됐다는 점을 확인했다.

## 1. 근거 (이미 측정된 사실)

| 측정 | 결과 | 출처 |
|---|---|---|
| Primary 읽기 vs Replica 읽기 (9/8, 앱 2대, A/B 각 3회) | TPS 중앙값 554.79 → 534.32/s, 평균 응답 22.40 → 55.21ms | README §7, `docs/load-test/replica-20260908.md` |
| 고정 20분 워밍업 재실험 (9/10) | TPS 536.700 → 531.683/s(−0.93%), 평균 응답 +6.85%, **종료 시 복제 지연 553·556·463초** | `docs/load-test/replica-warm20-20260910.md` |
| 포트폴리오 판정 | Replica "비채택" 사례 | 공통 백엔드 포트폴리오(10/1) |

그런데 로컬 운영 구성(`docker-compose.yml`)은 여전히 앱 읽기를 `mysql-replica`로 보낸다. 측정상 이득이 없고, 지연이 일관성 기준(삭제 즉시, 남의 행동 최악 30초)을 어긴다.

## 2. 결정

**앱의 읽기 DataSource를 Primary로 돌린다. 코드는 바꾸지 않는다.**

| 항목 | 변경 | 이유 |
|---|---|---|
| `APP_DATASOURCE_READ_JDBC_URL` | `mysql-replica` → `mysql-master` | Replica 지연을 읽기 경로에서 제거 |
| 풀 크기 | 쓰기 50 → **20**, 읽기 80 → **20**, 최소 유지 5 (사용자 결정, Codex 검토 반영) | 둘 다 Primary로 가면 260 > `max-connections=200`(실험 중 실제 `Too many connections`). 무중단 배포 중 앱 3대 × 40 = 120. 연결 한도가 아니라 DB(1코어·1GB) 능력 기준으로는 미측정 |
| sticky Primary | **그대로 켬** | 라우팅 의미는 없어지지만 댓글 캐시의 "글쓴이 우회" 신호로 계속 쓰임. 끄면 글쓴이가 최대 5초 자기 댓글을 못 봄 |
| 라우팅 코드 (`DataSourceConfig` 등) | 유지 | URL만 바꾸면 Replica 읽기를 다시 켤 수 있음 (되돌리기) |
| Replica 컨테이너 | **유지, 앱 미사용** (사용자 결정 추천안) | Replica 재실험용. 실수로 지운 것도 그대로 복제되므로 백업을 대신하지 못함. 복제 적용 CPU/IO는 계속 씀 |

풀 크기 근거: 지금까지의 부하 실험에서 쓰기 풀 50, 읽기 풀 80이 모두 쓰인 기록은 없음 — **미확인**. 20/20으로 줄였을 때 부하 성능은 재지 않았다(이번 범위 밖). 부하테스트 기준 구성이 바뀌므로 이후 부하 수치는 이전과 직접 비교하지 않는다.

## 3. 결과로 바뀌는 것

| 일관성 기준 항목 | 이전 | 이후 |
|---|---|---|
| 글 삭제 후 노출 (B) | 다른 사용자에게 Replica 지연만큼(부하 시 수백 초) | Primary 읽기 → 커밋 즉시 (상세 캐시 OFF, 게시판 캐시 제거) |
| 남의 글·좋아요 수 등 (C) | + Replica 지연 | Replica 지연 제거 |
| 댓글 (C) | 5초 캐시 + Replica 지연 | 5초 캐시만 |

## 4. 검증 계획

1. 앱 2대 기동, 앱 → Replica 연결 0 확인 (Replica의 `Threads_connected`/processlist에 앱 사용자 연결 없음), Primary 연결 수 140 이하.
2. 삭제 노출 재현: 게스트 글 작성 → app-1에서 삭제 → 쿠키 없는 사용자가 app-2 상세·목록 즉시 조회, 20회. 기대: 즉시 사라짐.
3. 전체 테스트 (로컬 `application.properties`는 읽기 3308 그대로 — 라우팅 테스트 유지 목적, 사용자 파일이라 변경 여부는 확인 후).

## 5. 문서 갱신

README §7 상단에 "현재 구성은 Replica 읽기를 쓰지 않는다(측정 근거·날짜)", `docker-compose.yml` 주석, 일관성 기준 공백 1 → 해소, CLAUDE.md는 Replica 언급 없음(변경 없음).

## 7. 결과 (2026-10-05)

Codex 검토(`.claude/docs/research/replica-reads-off-review-codex-20261005.md`) 반영: 풀 20/20·최소 5, 무중단 배포 여유, 복제 스레드는 Primary 연결을 1개만 씀(계획의 계산 정정), Replica는 백업을 대신하지 못함(실수로 지운 것도 복제됨), 댓글 삭제는 5초 캐시 때문에 즉시가 아님.

| 확인 | 결과 |
|---|---|
| 연결 | Primary: 앱별 10개(쓰기 5 + 읽기 5 최소 유지). Replica: 앱 IP에서 온 연결 0 |
| 게시글 삭제 → 다른 서버의 다른 사용자 (20회, 미리 조회해 둔 상태) | **20/20 즉시** — 삭제 후 첫 조회부터 상세·목록에서 사라짐(측정값 0.01~0.05초는 그 요청 자체 시간) |
| 댓글 삭제 → 다른 서버 (10회) | 다른 서버 캐시에 그 댓글이 있던 2회: 4.89초·4.98초 보임(캐시 TTL 5초). 8회는 다른 서버 캐시가 이전 시행에서 채워져 새 댓글이 처음부터 안 보여 측정 불성립 — 이것 자체가 "남의 댓글 최대 5초 늦게 보임"(C) |

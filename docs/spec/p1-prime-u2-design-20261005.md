# P1′ U2 서버 간 실시간 좋아요 — 설계 (2026-10-05)

상태: **승인 — 중간안, U2 끝까지 (2026-10-05)**. 구현 브랜치 `feat/u2-like-relay`.
결정 근거: `p1-prime-u2-alternatives-20261004.md` (유지 + Redis Pub/Sub, 기준값: 반대편 0/400, 끊김 후 재연결해도 5개 뒤처짐)
Codex 설계 리뷰 원문: `.claude/docs/research/u2-design-review-codex-20261005.md`

## 1. 목표 동작

```
[좋아요를 처리한 서버]
  LikeService (커밋)  →  컨트롤러
     ├─ ① 로컬 브로커로 전송 → 이 서버 시청자 (지금과 같음, Redis 문제와 무관)
     └─ ② Redis 채널에 발행 (큐에 넣고 바로 반환)
                         │
[다른 서버]  구독자 ◀─────┘ → 자기 origin이면 무시, 아니면 로컬 브로커로 전송 → 이 서버 시청자

[브라우저]  연결·재연결·탭 복귀·주기(약 30초) 때 현재 숫자를 한 번 조회해 덮어씀
           메시지마다 버전을 보고 더 오래된 숫자면 무시
```

| 보장 | 보장하지 않음 |
|---|---|
| 같은 서버 시청자는 지금처럼 즉시 (Redis 장애와 무관) | 메시지 유실 0 (Pub/Sub는 최대 1회) |
| 다른 서버 시청자도 연결 중이면 거의 즉시 | 끊긴 동안의 메시지 재전송 |
| 끊김·유실은 다음 재조회(최대 약 30초 또는 재연결)에서 맞춰짐 | 서버 간 전체 순서 |
| 늦게 온 옛 숫자가 새 숫자를 덮지 않음 (버전) | — |

## 2. 결정 사항 (Codex 리뷰 반영)

| # | 항목 | 결정 | 이유 |
|---|---|---|---|
| D1 | 설정 | `app.websocket.relay=local\|redis`, 기본 local, 잘못된 값이면 기동 실패 | U1과 같은 방식. 롤백 = local |
| D2 | 발행 위치 | `@SendTo` 제거, 컨트롤러에서 **명시적으로 로컬 전송 → Redis 발행**. STOMP 메서드는 `void` | 반환값이 있으면 Spring이 기본 목적지(`/topic/like/add`)로도 보내 버림 (Codex 지적). 로컬 전송과 Redis 발행은 서로 실패가 번지지 않게 분리 |
| D3 | HTTP 좋아요 경로 | `/api/test/likes/*`도 같은 발행 도우미 사용 | 지금은 HTTP 경로가 아예 방송을 안 함 → 실험 결과를 잘못 읽을 위험 |
| D4 | Redis 장애 시 기동 | redis 모드에서 Redis 없으면 **기동 실패** | U1 결정 B1과 동일. 조용히 local로 떨어지지 않음 |
| D5 | 순서 | **버전 컬럼 `reaction_version`** (post·comment). 좋아요 수를 바꾸는 같은 UPDATE에서 +1, no-op이면 그대로. 메시지·재조회 응답에 포함, 브라우저는 더 낮은 버전 무시 | 재조회와 중계가 같이 있으면 "늦은 옛 메시지가 방금 맞춘 숫자를 덮는" 경우가 실제로 생김. `updated_at`은 벌크 UPDATE라 갱신되지 않아 못 씀 (Codex 확인). 시간창 휴리스틱은 정상 이벤트도 버림 |
| D6 | 재조회 | `GET /boards/{slug}/{postId}/reactions?commentIds=...` — 로그인 불필요, **Primary에서 읽음**, 댓글 id가 그 글 소속인지 확인, 최대 100개, `Cache-Control: no-store`, 조회수 증가 없음 | Replica를 읽으면 지연된 옛 값으로 덮을 수 있음. 기존 상세·댓글 조회는 조회수·캐시·개인화가 섞여 재사용 안 함 |
| D7 | 재조회 시점 | 첫 연결·재연결·댓글 새로 그린 뒤·탭 복귀 + 보이는 동안 약 30초 주기 | 기준값 측정에서 재연결해도 안 맞춰짐 확인. 큐 드롭·구독 끊김은 TTL 같은 자가 회복이 없음 |
| D8 | 토픽 | 전역 하나 유지 | 낭비가 측정상 문제 될 때 분리 |
| D9 | 코드 재사용 | U1 브로드캐스터의 **패턴만** 재사용(단일 스레드 큐·드롭 지표·origin 무시), 별도 클래스. 공용 프레임워크로 추출하지 않음 | 두 기능이 같이 남을 때만 추출 |

## 3. 범위가 커진 이유와 선택지

내 초안(중계 + 재연결 재조회)에 Codex가 **버전 컬럼(D5)·주기 재조회(D7)·HTTP 경로 방송(D3)**을 더했다. Codex 제안 구현 순서는 20단위다.

| 안 | 내용 | 규모 | 남는 위험 |
|---|---|---|---|
| **전체 (Codex안)** | D1~D9 전부 | 큼 (스키마 변경 포함, 약 20단위) | 유실·순서 모두 보정 |
| **중간 (추천)** | D1~D4, D6, D7 + **D5 버전** — JS는 최소(버전 비교·재조회 함수 하나) | 중간~큼 | 같음. JS 테스트 범위만 축소 |
| **최소** | D1~D4 + 재연결 재조회만 (버전·주기 없음) | 중간 | 늦은 옛 메시지가 재조회 값을 덮을 수 있음, 유실 시 재연결 전까지 어긋남 |

**Claude 의견:** 최소안은 측정에서 드러난 "끊김 후 어긋남"만 고치고, 재조회와 중계가 함께 있을 때 생기는 순서 문제를 새로 만든다. 버전은 스키마 한 컬럼 + UPDATE 한 줄이라 비용 대비 효과가 크다. 그래서 **버전까지 포함한 중간안**을 추천한다.

스키마: 로컬은 `ddl-auto: update`라 컬럼이 자동 추가된다. 기존 행은 0으로 시작해도 문제없다(첫 변경부터 1씩 증가). 운영(CI) DB 반영 방식은 구현 1단계에서 확인한다.

## 4. 구현 단위 (중간안, 각 단위: 구현 → 테스트 → Codex 리뷰 → 커밋)

| # | 단위 | 테스트 |
|---|---|---|
| 1 | Post·Comment에 `reaction_version`, 좋아요 수 UPDATE·조회·보정 배치에서 함께 증가 | 실제 MySQL: 증가, no-op 불변, 좋아요·싫어요 공유, 보정 배치 증가 |
| 2 | `LikeResponse`·`LikeService`가 version 반환 | JSON 계약(enum 이름, 버전, no-op) |
| 3 | 재조회 API (서비스 + 컨트롤러) | 비로그인 허용, 소속 확인, 100개 상한, Primary 읽기, 조회수 불변 |
| 4 | `LikeRelay`(local/redis) + 발행기 + 구독기 + 설정 | 비차단·드롭·직렬화 실패 격리, origin 무시, 루프 없음, 모드별 빈, Redis 없으면 기동 실패 |
| 5 | 컨트롤러 재배선 (`void` STOMP, HTTP 경로 포함) | 성공 시만 발행, 기본 목적지 누출 없음 |
| 6 | 실제 Redis 통합 테스트 (게이트) | 두 인스턴스 전달, 재구독 |
| 7 | `detail.html`: 버전 비교 + 재조회 시점 | 브라우저 시나리오(수동 또는 스크립트) |
| 8 | §7 기준값 재측정 + 순서·Redis 구독 끊김 시나리오 추가 | 전후 비교 |

### 남은 한계
- Pub/Sub 최대 1회 전달. 연결이 살아 있는 동안 유실되면 최대 약 30초(주기 재조회) 뒤 맞춰짐.
- 재조회 API·전체 앱에 요청 빈도 제한 없음.
- 전역 토픽 유지(모든 글의 좋아요가 모든 시청자에게 감).
- 부하 상황 측정 아님(순차 요청).
